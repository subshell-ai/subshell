Web previews & screens lets you check a website or graphical app alongside the agent building it.

## Choose a view

| View | Use it to |
| --- | --- |
| **Web preview** | Check a website by interacting with it in your browser. |
| **Browser** | Watch a browser on the node without controlling it. |
| **Virtual display** | Control a browser or another graphical app on the node. |

The node running the subshell determines which features are available. You can
view them from a browser on another device or from Subshell Client.

## Enable web previews and displays on the machine

In the dashboard sidebar, open **Settings** → **Nodes**, select the machine
running your subshell, and open **Overview**. Its owner can change these settings;
an administrator manages them for the server's built-in node.

- **Allow web previews** enables web previews, saved services, and
  browser watching for every subshell on that node. No per-subshell option or
  virtual display is required.
- **Allow virtual displays** lets a subshell request a virtual screen at launch.
  Enabling this node setting alone starts no display processes. Each subshell
  that requests a display uses extra memory and CPU.

Both settings are off by default for new nodes and can be changed independently.

You need edit access to open an app or control a virtual display. View access
lets you discover available views and watch browser frames, so a person you've
shared with still sees all three rows in the picker, with the app and screen
rows disabled and saying "needs edit access" under each; the browser watch is
the one they can take. The header badge counts only what the reader can act on,
so it never numbers a row that will refuse them. Switching either feature off
prevents new operations; it doesn't stop your subshell or immediately close an
existing connection.

When a node has its switch off, the picker says so in gold and links to this
page, because a blank list reads as "nothing is listening" when the truth is
"this is switched off". The same line appears when the node itself answers that
way, with the node's own words attached. On the preview tab it also carries an
**Open node settings** jump straight to the switch. Only an owner (or an
administrator, for the server's built-in node) can turn it on.

## Use Web previews & screens from a Mac

If your subshell runs on a Linux node, follow the Linux steps below. Install
any display programs on that node; the Mac you're viewing from doesn't need them.

If the subshell runs on the Mac itself, use **Add service** for a web preview,
since automatic port and browser discovery require Linux. For graphical apps,
follow [Use a virtual display on macOS](#use-a-virtual-display-on-macos).

## Check a website

1. Start your project's dev server inside a subshell. Keep it listening on
   loopback; you don't need to expose its port to your network.
2. Use the Web previews & screens icon in the subshell header. A window icon
   means the subshell has a virtual display; otherwise the header uses a globe.
   The icon wears a count when there are views you could open and haven't saved
   yet: a discovered port with no Saved services row, plus the screen and the
   browser watch when the pane offers them. It's the picker's own data, so the
   number and the list can't disagree. Opening a view doesn't change it, since
   opening isn't saving: **Add service** is what takes a port's row out of the
   count, and a node switch or a refusal that leaves nothing to offer clears it
   outright.
3. In **Open web preview or screen**, choose the **Web preview** row for your dev server's port.
4. Check the site in the preview beside the terminal. Try navigation, forms,
   filters, and other interactions, then give your agent specific feedback.

## Add a service started elsewhere

Use a saved service when your web server runs outside the subshell or its port
isn't discovered automatically. You don't need a virtual display.

1. Use the Web previews & screens icon in the subshell header, then choose **Add service** under **Saved services**.
2. Enter the service's **Port** and choose **HTTP** or **HTTPS**. You can add a name
   to make it easier to recognize.
3. Leave **Host** under **Advanced** as `localhost` for a service on the subshell's
   node. For a service on another machine, enter a hostname or IP that the node can
   reach. Hostnames resolve on the node, not on the device viewing the dashboard.
4. Choose **Save service**, then select the saved row to open its workspace tab.

  <figcaption>Save a connection to a web service without creating a virtual display.</figcaption>

This also works for web services running on a macOS node, where automatic port
discovery isn't available. The subshell must be running and its node must have
**Allow web previews** enabled. HTTPS requires a certificate the node trusts and whose
name matches the host; Subshell doesn't bypass certificate checks.

Saved connections stay with the subshell across reloads and closed tabs. Use the
remove button beside a saved row to delete the connection and disconnect its open
views. Removing a connection doesn't stop the service. You need edit access to
add, open, or remove connections; people with view access can see the list.

## Arrange and refresh views

Drag preview tabs to keep several apps or screens visible together. Closing a
preview leaves its subshell and other previews running. Hidden previews release
their viewer connections and reopen when you select them again.

The viewer toolbar has refresh and a **More view actions** menu:

- **Maximize pane** enlarges that workspace pane. **Restore pane** appears
  directly in the toolbar while maximized.
- **Full screen** uses your browser's fullscreen mode. **Exit full screen**
  appears directly in the toolbar while active.
- **Open in browser tab** opens a web preview in a separate browser tab.
- **Close view** closes the current viewer.

Use the subshell header's Web previews & screens icon to open another view.

On a phone, previews use the workspace's tab strip without changing your desktop
split layout. From the standalone subshell page, the header icon takes you into
the workspace and opens the picker there.

## Use a virtual display on Linux

A virtual display gives GUI programs in a subshell their own screen, without a
physical monitor. Launch a browser there when you need to check browser storage,
login flows, or another graphical app.

A virtual display isn't a sandbox for the programs you run. They keep the
execution account's permissions. Don't enable it on a host shared with untrusted
local OS users; see [Preview security](/concepts/security#preview-security).

1. Install **Xvfb**, **x11vnc**, and **xauth** on the Linux machine running the
   subshell.
2. In the dashboard, open **Settings** → **Nodes**, select that machine, and
   open **Overview**. Turn on **Allow virtual displays**, enable **Allow Xvfb +
   VNC**, and select it as the **Default display provider**.
3. When launching a subshell, enable **Virtual display**. The form checks the
   selected node, which may be different from the device viewing the dashboard.
   If more than one provider is enabled, choose one under
   **Display provider**, or keep **Node default**. The list holds only what the
   selected machine's operating system can run, so Xvfb + VNC doesn't appear for
   a Mac and BetterDisplay doesn't appear for Linux; a machine that hasn't
   reported its OS yet is not treated as a verdict, and the list stays open.
   Missing requirements prevent launch until you resolve them or turn off
   Virtual display. After installing missing programs, choose **Recheck**.
   If the node refuses the display when you launch, the reason appears beside
   the **Virtual display** checkbox it belongs to rather than at the bottom of
   the form; switch the checkbox off and the line moves to the form's own
   message, because it still explains the launch that failed.
4. Launch your browser or GUI app from that subshell so it inherits the display
   settings. Install the browser on the node separately if it isn't available.
5. Use the window icon in the subshell header, then choose **Virtual display**.
   You can see and control the screen in its own workspace tab.

Changing the node’s default affects new subshells that use **Node default**. Each
subshell saves the provider it actually uses, so restarting keeps the same
provider and display size. Disabling a provider leaves existing displays
running, but prevents new displays and restarts that need it. A manual restart
is refused before stopping the current subshell.

You can [save the display choice in a preset](/presets/launch-defaults#save-a-virtual-display-choice).
Review it when changing nodes: if the new node can't provide the display, the
launch form turns the option off and explains why. A pending or failed
requirements check blocks launch until it can be checked or you turn the option off.

## Use a virtual display on macOS

Choose the **BetterDisplay** provider after following
[macOS display helper setup](/nodes/manage#macos-display-helper) on the node's
Mac. Both Subshell desktop apps ship the helper, and both reach it from the
assistant window's sidebar: open **Virtual Displays** to read what the Mac still
needs, then choose **Open Display Helper settings**. The helper stays disabled
until you enable it there and grant macOS permissions, and it keeps a menu bar
icon of its own that opens the same panel.

Unlike a private Linux display, a macOS virtual screen shares your login
session, keyboard focus, and pointer. Apps don't automatically open on it;
move their windows onto the screen before using its viewer. The helper's
**Disable helper** control stops capture and input without closing terminals.

You don't need to configure BetterDisplay as a VNC server or expose a VNC port.
Subshell handles the connection. Its local VNC listener has no separate password;
don't enable virtual displays on a Mac shared with untrusted local OS users.
See [Preview security](/concepts/security#preview-security).

## Watch browser frames

If a subshell runs Chrome or Chromium with remote debugging enabled on loopback,
the picker can show **Browser**. Select it to watch live frames of that browser.
This view is a screencast; use **Virtual display** when you need keyboard and
pointer control.

A view-only share can watch the browser discovered for that subshell. It cannot
select another browser port on the node. Close the preview tab when you're done.

## Launch a preview from another subshell

An agent can use MCP to start a helper on another enrolled node owned by the
same account. The example below uses a Linux node. A configured macOS node
can use `betterdisplay` instead; MCP can check its requirements but cannot
enable the helper or grant macOS permissions. Shared nodes and the server's built-in node aren't available
through the subshell token's node discovery tools.

1. Call `list_nodes` to choose an online node with `canLaunch: true`, virtual displays
   enabled, and an installed, working terminal harness. Call
   `get_node` with its ID to check the default provider, or include `provider`
   to check another enabled choice. Confirm `virtualDisplay.enabled` is true
   and its status is `ready`. If anything is
   missing, follow [Linux setup](#use-a-virtual-display-on-linux) on that node.
2. Call `create_subshell` with the node ID and a display:

   ```json
   { "harness": "terminal", "node": "NODE_ID", "name": "Website check", "screen": { "width": 1280, "height": 800, "provider": "xvfb-x11vnc" } }
   ```

3. Use `exec_in_terminal` with the returned subshell ID to start your development
   server and browser. Programs started there inherit `DISPLAY` and
   `XAUTHORITY`. Keep long-running programs in the background so the command
   can finish. For example, if Chromium is installed and your site is already
   serving port 3000 on that node:

   ```json
   { "subshell_id": "SUBSHELL_ID", "command": "chromium http://127.0.0.1:3000 > browser.log 2>&1 &" }
   ```

4. Call `list_subshell_views` with `subshell_id` to discover its views. In the dashboard,
   select the helper's Web previews & screens action and open its app or virtual display.
   Each opens in its own workspace tab. `open_subshell_view` can create a private
   connection path for a client, but it doesn't open a dashboard tab or return
   a screenshot.
5. Collect the results, then call `delete_subshell` to remove the temporary
   helper and its history. Stop any `watch_subshell_browser` interest with `on: false`
   when you finish watching.

See the [MCP tool reference](/mcp/tools#get_node) for arguments and readiness
fields, including harness health and SSH settings.

## Browser compatibility and private links

App previews use an isolated browser document so the website's JavaScript can't
read your dashboard's DOM, storage, or authenticated API responses. Target
cookies stay in the preview's server-side cookie jar. Sites that need browser
storage, service workers, JavaScript-managed cookies, or full browser login
flows should be checked in the node's browser through **Virtual display**.

The proxy preserves your app's paths rather than rewriting HTML or JavaScript.
If a dev server assumes it's hosted at `/`, configure relative asset URLs or a
matching base path. A target's strict content policy can also prevent embedding;
the virtual display gives you the browser's normal website context.

If the app rejects the preview's host or origin, check the app's allowed-host
and origin settings. Subshell doesn't bypass the app's access checks.

Treat a preview URL as a private access link. Anyone who receives it can use it
while its session remains valid, and closing a tab doesn't immediately revoke
a copied link. The server can read forwarded bytes and browser frames. See
[Preview security](/concepts/security#preview-security) for the trust boundaries
and [Architecture](/concepts/architecture#web-previews-and-virtual-displays) for the data path.

For implementation details, read [Web preview architecture](/developers/web-preview-architecture) and [Develop and extend web previews](/developers/web-preview-development).
