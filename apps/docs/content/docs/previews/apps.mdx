Open a website running on your node beside its subshell.

## Before you start

Follow [Preview prerequisites and setup](/previews/setup) for the node setting
and access you need. Automatic port discovery requires Linux; use a saved
service for a web server on macOS.

## Check a website

1. Start your project's dev server inside a subshell. Keep it listening on
   loopback; you don't need to expose its port to your network.
2. Use the Web previews & screens icon in the subshell header. A window icon
   means the subshell has a virtual display; otherwise the header uses a globe.
   Its badge counts views you can open that haven't been saved: discovered ports
   without a saved service, plus an available screen and browser watch. Opening
   a port doesn't save it; **Add service** removes that port from the count.
3. In **Open web preview or screen**, choose the **Web preview** row for your dev server's port.
4. Check the site in the preview beside the terminal. Try navigation, forms,
   filters, and other interactions, then give your agent specific feedback.

## Add a service started elsewhere

Use a saved service when your web server runs outside the subshell or its port
isn't discovered automatically.

1. Use the Web previews & screens icon in the subshell header, then choose **Add service** under **Saved services**.
2. Enter the service's **Port** and choose **HTTP** or **HTTPS**. You can add a name
   to make it easier to recognize.
3. Leave **Host** under **Advanced** as `localhost` for a service on the subshell's
   node. For a service on another machine, enter a hostname or IP that the node can
   reach. Hostnames resolve on the node, not on the device viewing the dashboard.
4. Choose **Save service**, then select the saved row to open its workspace tab.

The subshell must be running. HTTPS requires a certificate the node trusts and
whose name matches the host; Subshell doesn't bypass certificate checks.

Saved connections stay with the subshell across reloads and closed tabs. Use the
remove button beside a saved row to delete the connection and disconnect its open
views. Removing a connection doesn't stop the service. People with view access
can see the list but can't open or change its connections.

## Configure an app preview

<figure className="docs-screenshot">
  <ImageZoom src="/screenshots/preview-settings.png" alt="Configure preview dialog, with Rewrite app URLs and Rewrite redirects enabled, Pass the preview host disabled, and reset, cancel, and save controls." width="2144" height="1736" loading="lazy" decoding="async" unoptimized />
  <figcaption>Personal settings remembered for this app on this node.</figcaption>
</figure>

In the subshell header's **Open web preview or screen** dialog, select
**Configure preview before opening**, then choose a discovered port or saved service. For an app that's already open, use
**More view actions** → **Configure preview** in its toolbar.

| Setting | Default | What it changes |
| --- | --- | --- |
| **Rewrite app URLs** | On | Routes supported app URLs through the private preview path. |
| **Pass the preview host** | Off | Sends your browser's preview host to the app instead of the target host. Use it only when the app expects that host. |
| **Rewrite redirects** | On | Keeps redirects to this app under the preview path. |

Choose **Save and open** to save your choices and open a fresh preview.
**Reset to defaults** removes the saved choices and opens a fresh preview with
the defaults above. **Cancel** keeps the current preview.

These settings belong to your account and follow you across devices and
subshells for the same node, host, protocol, and port. They don't change anyone
else's preview or grant access to a target. A saved service and a discovered
port share settings when they identify the same target.

## Browser compatibility and private links

App previews use an isolated browser document so the website's JavaScript can't
read your dashboard's DOM, storage, or authenticated API responses. Target
cookies stay in the preview's server-side cookie jar. Sites that need browser
storage, service workers, JavaScript-managed cookies, or full browser login
flows should be checked in the node's browser through a [virtual display](/previews#choose-a-view).

With **Rewrite app URLs** enabled, Subshell rewrites supported HTML attributes,
CSS URLs, and module imports. It also adds a browser compatibility script for
common requests such as fetch, XMLHttpRequest, WebSocket, and EventSource.
This helps apps that assume they're hosted at `/`, but it doesn't make every
app compatible. A target's strict Content Security Policy can block the
compatibility script or other resources. Preview settings don't relax the
sandbox.

If the app rejects the preview's host or origin, check the app's allowed-host
and origin settings. Subshell doesn't bypass the app's access checks.

> [!WARNING]
> Treat a preview URL as a private access link. Anyone who receives it can use it
> while its session remains valid, and closing a tab doesn't immediately revoke
> a copied link. Remove a saved service to revoke its connections, or remove
> access or end the subshell to revoke existing access. Turning off previews on
> the node doesn't immediately revoke existing connections.

The server can read forwarded app traffic. See
[Preview security](/concepts/security#preview-security) for the trust boundaries
and [Architecture](/concepts/architecture#web-previews-and-virtual-displays) for the data path.

For implementation details, read [Web preview architecture](/developers/web-preview-architecture) and [Develop and extend web previews](/developers/web-preview-development).
