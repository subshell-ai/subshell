---
title: Work over SSH
description: Open agents and terminals in remote folders using SSH from Subshell Client or a machine you own.
---

Subshell can run agents and terminals in a remote folder through an SSH connection.

The destination runs the `subshell` runtime and tmux. It does not need node enrollment, a Subshell service, or a network connection back to your server. Your SSH keys stay on the computer that makes the connection.

## Prepare the remote host

On the computer that will connect, add a concrete host alias to `~/.ssh/config`:

```sshconfig
Host devbox
  HostName devbox.example.com
  User you
  IdentityFile ~/.ssh/id_ed25519
```

Verify `ssh devbox` works from that account. Complete host-key verification there and unlock your SSH key if needed. Subshell does not answer interactive SSH password or MFA prompts.

On the destination, install tmux and the `subshell` CLI binary for its operating system and architecture. Use the CLI node assets on the [Subshell releases page](https://github.com/subshell-ai/subshell/releases). Make the binary executable and put it on the destination account's login-shell `PATH`. You do not need to run `subshell setup` or enroll the destination.

Install and sign in to any agent CLI you want to use on that destination. A terminal needs no agent installation.

## Connect from your computer with Subshell Client

1. In your server's dashboard, open **Settings → SSH Connections**. Any signed-in user can manage their own connections.
2. Give your computer a recognizable name and select **Add computer**.
3. Copy the server address and pairing code into **SSH Connections** in Subshell Client. A fresh install also offers **Work on a machine over SSH**.
4. Check the server address and confirm that you trust the server and the account that created the code to use your computer's SSH access. Select **Connect this computer**.
5. Open the dashboard. Choose **New subshell → SSH host**, then choose your computer under **Connect from**.

Pairing codes expire after five minutes and work once. After pairing, Subshell Client remembers a scoped connection credential locally, so **Reconnect** does not require another code. Keep the app open while using the connection. **Revoke access** in the server's Connections settings invalidates that credential.

The computer is not enrolled as a node by this procedure.

## Connect through an existing node in the browser

In **New subshell → SSH host**, choose a connecting machine you own. Subshell uses the SSH configuration, keys, and account on that machine, which may differ from the computer running your browser.

Shared nodes and other users' nodes cannot supply your SSH connection. Admins can also choose the server account when server launching is enabled and the server machine is not in maintenance.

## Open a remote folder

1. Choose a host alias. If none appears, follow the configuration example on the connecting machine and select **Refresh hosts**.
2. Review the destination address, destination account, and connecting account, then connect. A failed connection explains what to fix, including a missing remote runtime.
3. Enter or browse to the remote folder. Choose an installed agent or terminal, optionally apply a preset and prompts, then start the subshell.

The same form is available when creating a workspace or adding a pane. Existing connections appear directly in the host picker.

Use **Remember this host and folder** to save the host and folder in your account. A saved location reuses a matching live connection or reconnects through the same connecting machine. If its SSH alias now points to a different host, port, or account, Subshell refuses to silently switch destinations; connect to the new destination and save a new location deliberately.

## Return to remote work

Remote panes appear alongside your other subshells, labelled with their SSH host. They use ordinary pane permissions, logs, sharing, and MCP access.

If a connection drops, the pane shows it as unavailable. **Reconnect** opens recovery in place, preserving the pane or workspace you were viewing. A new connection reconciles the destination's surviving panes. Disconnecting SSH leaves remote tmux panes running, but Subshell cannot establish their current state until it reconnects. Requests whose results were lost are not replayed automatically.

Use **Settings → SSH Connections** for connection history and disconnect controls. If Subshell Client itself disconnected, reconnect it in its **SSH Connections** screen before reconnecting the remote host.

## Limits

- Destinations must run Linux or macOS with a POSIX shell.
- SSH authentication must work without interactive prompts. Configurations requiring `ProxyCommand` or port forwarding are refused; bounded `ProxyJump` chains are supported.
- The destination runtime is installed manually. Subshell does not install software on a destination automatically.
- Desktop pairing requires HTTPS, except for a server reached through a loopback HTTP address.
- Moving an existing agent conversation and Git state between different hosts is not supported.
