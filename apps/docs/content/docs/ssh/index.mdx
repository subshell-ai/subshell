Reach any Linux or macOS machine you can already reach with SSH, and work on it as if a Subshell node lived there, without enrolling one.

## How it works

```
browser → control plane → one of your enrolled machines (runs ssh)
        → SSH session → `subshell runtime-serve` on the destination → ordinary panes
```

The runtime is a session-scoped mode of the same `subshell` binary your node runs. On the destination it drives tmux, owns the pane logs, and answers commands over the SSH link itself. There is no enrollment, no node key, no service, and no network port opened on the destination: the SSH link is the whole connection, and the session ends with it.

Everything the destination needs is SSH that already works from the connecting machine's account: a key the destination accepts, and host trust that is already in place. Subshell never learns your private keys; they stay in the OS account on the connecting machine, where SSH already reads them.

## Connect

Open **Connect over SSH** in the sidebar. The page walks the journey:

1. **Pick the connecting machine.** Only your own enrolled machines are listed, because the SSH runs as your account on that machine's terms. An admin's access to someone else's machine is not ownership, and a shared node is not yours to broker with.
2. **Pick the host.** The machine lists the alias names from its own SSH config; config contents never leave the machine.
3. **Review and connect.** The page shows the concrete `host:port`, the destination account it resolves to, and the connecting account. **Connect** proves reachability and the runtime's presence in the same step, and a refusal says what to fix.
4. **Choose the folder.** The picker browses the destination's directories over the live session, showing the absolute path throughout.
5. **Launch.** A terminal pane opens in the chosen folder and appears everywhere ordinary panes appear: the rail, the subshells list, and the detail page with its log, sharing, and workspace tiles. The pane's page names its destination and the machine it was brokered through, in a line assembled from the server's records, never from anything the terminal displays.

Sessions you opened stay on the same page as your own history, newest first. Closing a session ends the SSH link; panes you launched keep running on the destination under the runtime's tmux socket, and a later session to the same destination finds them again.

## What the panes get

A pane opened this way is an ordinary subshell: a normal working directory, a normal log, and its pane's own MCP credential, so it can report on itself, extend its token, read sibling panes, and use channels exactly like a pane on an enrolled node. The credential's traffic reaches the control plane through the session itself, never through a network route the destination must have.

## When the link drops

If the SSH session dies, the session is marked lost and its panes read unavailable, never completed: the destination's tmux and panes are untouched, and the next session to that destination reconciles them. Nothing is replayed automatically; an uncertain result stays uncertain. While the connecting machine itself is offline, browsing, launching, and closing are refused until it is back.

## Limits

- Linux and macOS destinations with POSIX shells. Windows destinations are not supported.
- The destination needs the `subshell` binary on the connecting account's PATH. A missing runtime is reported by name at connect time with exactly that remedy; Subshell never installs anything on a destination for you.
- The connecting machine reads your account's SSH config for alias names and the resolved destination. Configs that need a `ProxyCommand`, port forwarding, or interactive password or MFA entry are refused by name; keys-only auth through the machine's existing trust is the supported shape, with an already-unlocked authentication agent and a bounded `ProxyJump` chain carried as-is. First-time host trust happens on the connecting machine, outside Subshell.
- Sessions are personal: they live in your account, and their panes follow the ordinary subshell sharing rules.

## SSH connections for agent panes

Settings → **SSH** (server administrators) is a separate surface for agent-driven work on destination machines. A human configures each connection, tests it against a fixed benign probe, and grants selected agent panes access to it; an agent never configures connections, never sees credentials, and cannot use a connection nobody granted it. With a grant, a pane can run structured commands and open managed interactive terminals on the connection; the exact arguments are in the [MCP tool reference](/mcp/tools).

Grants bind one connection to one pane's current credential. They do not spread to child panes, and a restarted pane holds nothing until a human grants it again. Revoking stops new work immediately, fences input already in flight at the connecting machine, and reaches nothing outside that grant. Human takeover of a managed terminal controls input, not secrecy: agent reads and writes stop while a human holds it, and recorded output is transcript data, not a confidential buffer. Unknown, changed, and revoked host keys fail closed, and remote output is always rendered as data.
