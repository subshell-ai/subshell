A **node** is a machine that runs agents for you. It runs the `subshell` node daemon and nothing else: it has no UI, no database, and no decision logic of its own. The control plane keeps the web interface, the database, the decision logic, and the terminal transport, and the node executes what the plane sends. Your control-plane host can run agents too if you allow it, and when it does, the host is also a node.

The point of a node is that a subshell can live on any machine you own and look the same from anywhere you are. The browser cannot tell a remote pane from a local one. The control plane relays the same replay, resize, and keystroke frames either way, so xterm.js cannot tell whether the bytes came from tmux on the plane's host or from a machine in another room.

## What enrolling a node delegates

Read this before you add your first node. Registering a machine grants this control plane the right to run arbitrary commands on it, under the OS user the node runs as. That delegation is the feature: the plane launches tmux, writes the files a launch needs, and reads back what the harnesses report. It also means:

- Whoever owns that OS user owns every pane launched there: its files, and the subshell's bearer token, which rides in the launch command's arguments and is visible to any local process that can read `ps` output.
- The control plane's command-signing keypair rules every enrolled node. A control-plane compromise is a compromise of all of them at once.
- A node's own bearer key is narrow on purpose: it can do nothing on the REST API. Its entire reach is impersonating that one node on its WebSocket.

## How the link works

The link is dialed outward by the node. The control plane never connects to a node, which is why nodes work behind NAT and on laptops. Commands travel from the plane to the node as signed envelopes, and the node verifies every one before executing anything, so a compromised relay cannot forge work for it. Events travel back unsigned because the node key on the socket already authenticates them. Signing proves who sent a command, when, and which node it is for; it is authorization, not confidentiality. Confidentiality lives in the link itself: since protocol 14, every connection negotiates a per-connection key as it opens, and from then on the socket carries only ciphertext.

The trusted-network posture still governs how you deploy, because each side trusts the key it pinned at enrollment rather than a certificate authority: keep nodes on the same VPN or tailnet as the plane. [Node protocol](/reference/node-protocol) is the full contract, and the security consequences are in [the repository's threat model](https://github.com/subshell-ai/subshell/blob/main/docs/security.md#6-nodes).

An offline node is never treated as crashed. Launches onto it are refused while its row keeps its history, and the UI says "node unreachable", not "failed".

## The machine that hosts the control plane

Your control-plane host appears in the Nodes list as a node of its own. An admin names its row, and the default name is **Server**. The row is always online by definition, and the host runs no node daemon. It is managed through the server's own settings pages rather than the per-node controls. Those controls refuse it by design, because the row names the same machine as the plane.
