Give another user view or edit access to your node, and see what each grant level confers.

Sharing a node extends your machine's command surface to somebody else's workloads. A share does not open a folder or a view; it opens launch. What a grantee launches runs on your hardware, under the OS user your node runs as, with all the reach that implies. As the owner, you see grantees' work as a bare count: what they launch stays private to them unless they share it back. Admins resolve to edit on every subshell, and the machine's own OS users see every pane. This page lists what each grant confers, what stays yours, and what neither the owner nor the grantee controls.

## The one asymmetry to know

Any node share, even view, lets the grantee launch their own subshells on your machine. There is no read-only level of node sharing. What they launch is private to them: invisible to you unless they share it back, on the separate axis of [subshell sharing](/use/sharing). Node shares and subshell shares are independent axes. Sharing a node never hands out subshell tokens, and sharing a subshell never grants anything about its machine.

The two levels:

| Grant | What the grantee can do |
|---|---|
| view | Launch their own subshells on the machine. That is already running arbitrary work there. |
| edit | Everything above, plus configure the node: re-checks (re-probing for agent CLIs), the start / install / restart service controls and log reads on [the node's page](/nodes/manage), debug-logging flips, and updates. |

These stay yours no matter what you grant:

- Sharing itself: re-granting and revoking happens only from your node's page.
- Renaming the node.
- Deleting it, which revokes its key.
- Stop and uninstall of the node: an edit grantee may interrupt a machine you shared with them, but making it unreachable until someone acts at the machine itself is a different act.
- Repointing it at a different control plane.
- Maintenance and the directory allowlist.

A grant that turns out to have been too wide is revoked by clearing it in the same dialog that set it. Anything the grantee already launched keeps running: revoking a share does not terminate their subshells. [Maintenance mode](/nodes/manage) does.

## Granting access

From the node's page, open the sharing dialog and grant view or edit to specific users or to Everyone, which is every signed-in user on the instance. Node lists are small, per-user places, so the picker names everyone.

## The control-plane host's row

The control plane's own machine (the row named **Server**) starts out shared to Everyone at edit. That seeded default makes a fresh instance usable by everyone it admits, so the row is visible and launchable by default. Removing that share is how an admin narrows the plane's host to themselves, and the removal sticks: boot seeding never re-adds a share an admin deliberately removed. Once removed, the narrowing applies to admins too, because the admin boost confers management and never launch. An admin who removed the share is refused when launching there: the refusal names the node and says no one is granted launch access on it. The remedy is a share, granted from the row they can still see.

## What the grantee cannot see

Two disclosures run the other way, and both are deliberate:

- A view grantee may launch here without learning anything about the machine: how it is supervised, where its files live, what it logs. That runtime detail appears only for the owner and for edit grantees.
- The machine's owner sees a count, not the work. How many subshells are running there is visible to whoever manages the node, which is how an owner learns the price of maintenance or a revocation. A grantee's subshells stay theirs unless they share them.

And one disclosure is outside both of your controls: whoever owns the node's OS user at the machine (you, presumably) can read every pane launched there and the bearer token in each launch's arguments. A node share is therefore also a statement that the machine's local users are trusted.
