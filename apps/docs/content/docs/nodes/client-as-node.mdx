---
title: Subshell Client as a Node
description: "Register your own machine as a node from the Subshell Client desktop app, without a terminal."
---

Subshell Client is two things in one app: your interface to a control plane, and the place where the machine you are sitting at becomes a node. The second half lives in a separate window, **Window → This machine…**, an assistant that registers this machine: you paste a setup key and name the machine, and it installs the node binary, enrols it, and gets it running in the background. There is no terminal and no download step, because the binary ships inside the app.

## Who needs this window

If you launch subshells on the same machine you watch them from, which is most people, this is the easy path, and it is the one the desktop install puts you on. If you only watch subshells that run somewhere else, you never need to open this window at all. Its existence is the entire "node functionality" toggle: there is no mode to set, and an app that never opened it is a pure client.

The machine hosting the control plane has its own built-in node row, and you do not enroll that one here. This window registers the machine Subshell Client runs on, with whichever control plane you point it at.

## The assistant screen by screen

The assistant asks one question per screen, in order:

1. **Connect**: the control plane's address. It is asked first because every later screen answers a question about a plane that has not been named yet. This is the address the app's other window loads.
2. **Install the node**: the bundled binary is installed to `~/.local/bin/subshell`, the same managed copy the command-line path writes, so one machine cannot end up with two of them. Replacing an existing binary goes through the node's own update transaction, which records a rollback point. If the installed binary is too old to have one, the screen reports that plainly instead of pretending otherwise.
3. **Enroll**: you paste the two values the plane's **Nodes → Add node** dialog shows on its **Desktop App** path: the server address and a single-use setup key. [Adding a Node](/nodes/add-node) covers what a key is and how long it lives, and the key stays listed on the Nodes page until it is used. The screen also asks a **Node name**, and it is required: naming moved off the control plane and onto the machine that knows what it is called. The node generates its identity on this machine and consumes the setup key in the exchange. It keeps no copy of the key, which lives 24 hours at most. The long-lived **node key** the exchange returns is stored only in the node's private 0600 config file, its one home.
4. **Service**: the app offers to start the node at login and keep it running, as a systemd user unit on Linux or a launchd agent on macOS.
5. **Connected**: the node's live state, whether it is online and what the service manager says, and a **Re-enroll…** entry point for deliberately doing step 3 again.

tmux is a gate, not a caption: while the machine has no tmux, the enroll and service buttons stay disabled, because a tmux-less node would come up online and then fail every launch. The screen names the install command for your platform; installing it and pressing Refresh re-arms the buttons.

> [!caution] Enrolling twice is destructive
> A second enrollment overwrites the node's saved configuration, registers a second node on the control plane, and discards the current node key, whose only home was that overwritten file. The app will not run an enroll until you confirm exactly that. If you are already enrolled and only need to reach a plane that moved to a different address, that is repointing ([Managing a Node](/nodes/managing-a-node)), which keeps the machine's identity and mints nothing.

The window can also take the node back out: reset removes the service and the enrollment. It can open the control plane in your real browser, for anything a webview is wrong for, such as sharing a subshell or using passkeys. Stopping or uninstalling the node from here is deliberately not offered: both would end the very connection their own undo would ride, and that decision belongs to the node's page. **Restart** is the one service act the assistant keeps, because an offline node can only be revived at the machine itself, and its confirmation names which subshells it will take down.
