Inspect a node's runtime and execution settings.

## Open the node

In the server dashboard sidebar, open **Settings** → **Nodes**, select a machine, and open **Overview**. Check its online state, maintenance state, runtime, and installed harnesses before launching work.

The harness list on a node's page is cached from its last detection, so it may describe an older state. Use **Re-check** to request fresh detection.

The overview shows the operating system, release, architecture, hostname, CPU model, logical CPU count, and total memory when available. These describe host capacity, not current free resources or container limits. Offline nodes show how long ago they were last seen, or that no connection has been recorded, and retain their last known specs. MCP exposes the same hardware report through `list_nodes`; see [MCP tool reference](/mcp/tools#list_nodes).

## Cross-agent guidance

On the node's **Overview** page, find **Cross-agent communication**. Only the node owner can edit this guidance; a server admin manages it for the server's own node.

1. Fill in **Notes for calling agents** with context that helps an agent choose and use this machine. For example: “Use this node for Linux builds; run tests with Bun.” Notes accept up to 8,000 characters.
2. Select **Save guidance** to save the notes.
3. Under **Recommended starting directories**, select **Add directory**, enter or browse to an absolute path, then select **Add directory** again to save it. Repeat for other suggestions. Use the remove button beside an entry to remove it.

Adding or removing a directory also saves any pending notes. Agents read both fields through MCP discovery. Directory suggestions don't grant or restrict access; the node's [Directory restrictions](/nodes/directories) still apply.

## Apps, browsers, and virtual displays

In the server dashboard, open **Settings** → **Nodes**, select a machine, and open **Overview**. Its owner can change these settings; a server admin manages them for the server's built-in node.

- **Allow web previews** lets authorized viewers open web apps and saved services, and watch browsers in any subshell on that node. See [Web previews & screens](/guides/preview#check-a-website).
- **Allow virtual displays** lets subshells request a screen for graphical apps on a machine without a monitor. Each display uses extra memory and CPU; web previews don't need one. See [Use a virtual display on Linux](/guides/preview#use-a-virtual-display-on-linux) for requirements and setup.

Under **Allow virtual displays**, enable the providers you want this node to
use and choose a **Default display provider**. Each enabled provider can be
selected when starting a subshell. **Xvfb + VNC** requires Linux.
**BetterDisplay** requires macOS 14 or later and the separately enabled helper described below. The card checks requirements on the selected node,
which may be a different machine from the one displaying the dashboard.

Changing the default doesn't change existing subshells: their restarts retain
the saved provider. Disabling a provider prevents new allocations and restarts
that need it, while existing displays keep running. Enabling a provider starts
no processes until a subshell requests a display.

The switches work independently. Both are off by default. The cards explain when a feature is disabled or required display programs are missing. Turning either setting off blocks new operations without stopping existing subshells or immediately closing existing connections.

## macOS display helper

Subshell Client and Subshell Server both bundle **Subshell Display Helper**.
Either desktop app can manage the same helper on that Mac. Installing or
setting up either app doesn't enable the helper, request its permissions, or
register it to start at login.

Use the Mac that runs the selected node, with your macOS account signed in.
Keep another screen as the main display; the helper refuses a virtual screen
that is main or mirrored. A Mac whose only screen is the new virtual display
isn't supported by this provider.
BetterDisplay must be installed and running with CLI access enabled and a
license or trial that supports virtual screens. Subshell doesn't install or
purchase BetterDisplay for you. See [BetterDisplay's integration guide](https://betterdisplay.pro/guide/integration/).

1. On that Mac, open **Subshell Client** → **Virtual Display Helper…** or
   **Subshell Server** → **Virtual Display Helper…** from the macOS menu bar.
   This opens settings; the helper stays disabled until you choose otherwise.
2. Read the shared-desktop warning, then choose **Enable helper**. This also
   registers the helper to start when you sign in. It can keep running after
   you close the desktop app. If the panel reports pending background approval,
   choose **Open login items…** and allow it in System Settings.
3. Choose **Allow screen recording…** and **Allow accessibility…**. In macOS
   System Settings, grant both permissions to **Subshell Display Helper**.
   Screen Recording lets it capture the virtual screen; Accessibility lets it
   send keyboard and pointer input. Subshell can't grant these permissions
   through node settings or MCP. If macOS requires a restart, choose **Quit
   Helper** from the helper's display icon in the menu bar, reopen its settings
   through either desktop app, and enable it again.
4. In the server dashboard, open **Settings** → **Nodes**, select that Mac,
   and open **Overview**. Enable **Allow virtual displays** and **Allow
   BetterDisplay**, then choose it as the default if desired. Choose **Recheck**
   if requirements still show as missing.
5. Start a subshell on that node with **Virtual display** and **BetterDisplay**
   selected. Open its screen through **Web previews & screens**.

macOS displays share the same desktop, keyboard focus, and pointer. Apps and
notifications on the virtual screen can appear in its stream. This isn't a
separate login session or a sandbox. Only enable it for people you trust to
control that Mac. Keyboard input requires a focused window entirely inside the
virtual screen; click that window before typing.

Unlike Linux's `DISPLAY` environment variable, macOS doesn't automatically
place an app on the subshell's screen. Move the app's window onto that screen
on the Mac, or use the app's own display-selection support. Programs inherit
`SUBSHELL_DISPLAY_UUID` and `SUBSHELL_DISPLAY_NAME` to identify the target.
Capture runs at up to five frames per second; audio and clipboard sharing
aren't supported. Native letter shortcuts use the Mac's ANSI key positions;
non-US keyboard layouts may interpret shortcuts differently.

To stop access, open the same panel and choose **Disable helper**, or choose
**Disable Helper** from its menu-bar icon. This disconnects all helper captures
and stops input for both desktop apps, and unregisters startup at login.
Your terminal subshells keep running. macOS permission grants remain in place;
you can revoke them separately in System Settings. **Quit Helper** also
disables it. Existing virtual screens can remain until their subshells close
or recovery can contact BetterDisplay again.

Turning off **Allow virtual displays** in node settings blocks new allocations;
it doesn't replace the helper's immediate disable control. If the Mac has no
running helper, the node reports that requirement instead of launching it.

## Names and ownership

Node names are display labels. Renaming a node doesn't change its identity, and launch pickers use the current display name.

The server host's node is named **Server** by default. Its internal ID remains `local` even if the administrator chooses another label.

Node owners manage the machine's settings. A share may allow launching there without granting ownership of service, directory, or enrollment controls.

## Outgoing SSH

In the server dashboard, open **Nodes**, select your node, and find the **SSH** card on its overview. **Allow SSH** lets Subshell make outgoing SSH connections from this node and use its SSH agent to supply keys to other nodes. It doesn’t enable incoming SSH access to the node.

Only the node’s owner can change this setting. An administrator manages it for the built-in node on the server host. Turning it off prevents new outgoing connections and stops the node from supplying keys, including to active connections.

You can also enable it when starting an SSH subshell: the connection form explains the change before you submit. See [Connect over SSH](/guides/ssh).

With SSH allowed, the card gains **Allow wide port forwards**. While it's off, local and dynamic port forwards bind the node's own loopback address, so only programs on that node can use them. Remote forwards listen on the SSH destination under its SSH server's policy. See [Port forwards](/guides/ssh#port-forwards) for examples and bind-address rules. Turning it on lets a launch bind a port other machines can reach, which routes their traffic through that connection. It's off by default and sits behind the same owner-only gate as **Allow SSH**; turning it off affects new launches, while forwards already running keep going until their subshell closes.

## Service and logs

Where you have management access, review the service and log sections. A node may be online from a terminal process even when no service is installed.

The Service card shows **Start** or **Stop**, and **Install service** or **Uninstall service**, based on the node's reported state. **Restart** is available when a service manager runs the node. Only the node's owner can stop or uninstall its service.

Restart, Stop, and Uninstall service ask for confirmation before making changes. The dialog explains whether subshells may close and whether you'll need access to the machine to bring the node back.

On the machine, use:

```bash
subshell status
subshell service status
```

`status` describes the daemon's recorded state; service status asks the service manager. Avoid `status --probe` during normal inspection because it connects as the node and can displace a running connection.
