The point of an agent is that it works while you do not. Notifications tell you when that stops being true: a turn is done, a permission prompt is waiting, or the process died. Every notification is targeted and gated: it goes only to devices belonging to the subshell's owner, and only when the owner's switches allow it.

## Notification events

Six events produce notifications, and the wording identifies which one occurred:

| What you receive | When it fires |
|---|---|
| **Done, waiting for you** | the agent finished its turn and the pane sits idle |
| **Needs your approval** | the agent paused mid-turn, waiting for a permission or an answer |
| **Subshell exited** | the pane's process ended and no auto-restart is configured |
| **Crashed, auto-restarting** | the process died on a subshell that will be brought back |
| **Crashed** | it died and the auto-restart ladder has given up |
| **Stopped for node maintenance** | the [node's owner](/nodes/maintenance) took the machine out of service; it is not a fault of yours or the agent's |

The first two come from the agent. The last four come from the server watching the pane and the node, which is why they describe deaths that no user action caused.

## How events are detected

Detection runs in two tiers, and the agent determines which one applies:

- **Native hooks.** Claude Code launches with hooks that report each turn's end (`Done, waiting for you`) and each pause for input (`Needs your approval`) directly, at the moment they happen. Only Claude Code can report `Needs your approval`; it is the only built-in agent with a way to.
- **The quiet-output fallback.** Every other built-in agent (Codex, opencode, Hermes, Pi, and a plain terminal) is covered by a heuristic: when its pane's output has been silent for 20 seconds, the turn is treated as over. The fallback reports `Done, waiting for you`, and it never claims that approval is needed, because it cannot know what the silence means.

Either way, the report is the subshell speaking about itself with its own credential: a harness can ring its own bell and no other subshell's. When a report lands, the subshell also shows a "waiting for you" marker, pinned to the top of your sidebar. Typing in its pane clears the marker, and so does new output once the turn has settled for a few seconds.

## The two switches

Nothing is pushed unless both agree:

1. **Your account-wide switch**: Preferences → Notifications. Off means no notifications at all, whatever any bell says.
2. **A subshell's bell**: its ⋯ menu toggles it. The item reads **Mute notifications** while the bell rings and **Notify when done** while it is quiet. New subshells start with the bell on; mute the noisy ones individually. Restarting keeps whichever setting the subshell had.

The bell is owner-only. Sharing a subshell never transfers its bell to the grantee, and pushes never go to anyone but the owner's devices: sharing widens who can watch, never who receives a notification.

## Where notifications arrive

- **From a browser**: enable push on the device (Preferences → Notifications). Each browser on each device subscribes for its account, and the server's keys are generated per instance with nothing to configure. On iPhone, web push is available only for a web app **added to the Home Screen**; a normal Safari tab cannot be pushed. Android and desktop browsers push from the site directly.
- **From the [mobile companion](/get-started/mobile)**: native push with the app-icon badge and lock-screen actions.
- **From the Subshell Server desktop app**: when one of your belled subshells starts waiting, the app posts its own native notification. No push subscription is involved, and the desktop app needs none.

A tap opens that subshell's page. A newer event for the same subshell replaces its earlier notification rather than stacking.

> [!note] Delivery is best-effort
> Delivery failures never break a launch or a pane. An endpoint the push gateway reports as dead is pruned automatically, and the subshell keeps working regardless.
