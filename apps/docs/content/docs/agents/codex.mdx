Codex is OpenAI's agentic coding CLI. As a Subshell harness it runs the interactive TUI in a pane, with the [subshell MCP server](/automation/mcp-server) wired into every launch. The `~/.codex` directory that holds your Codex sign-in and configuration is never touched.

## Finding the binary

Subshell resolves `codex` on the machine that will run the pane. It first tries the `codex` on the PATH there, which includes what a login shell would find. It then checks its known install locations under your home directory, the npm and bun global bins among them. Set `CODEX_PATH` on that machine's environment to name the binary explicitly.

If detection finds nothing, [Installing Agent CLIs](/agents/installing-agent-clis) covers the one-line installer, and the [vendor CLI docs](https://learn.chatgpt.com/docs/codex/cli) describe the manual path.

## What a launch looks like

A bare Codex launch opens the interactive TUI, so that is what a subshell runs. Settings arrive as per-invocation flags. The [preset editor](/use/presets) offers model (`-m`), sandbox (`-s`: `read-only`, `workspace-write`, or `danger-full-access`, which the editor labels "Full access"), and approval behaviour (`-a`), and any preset or one-off flags ride along after them.

Two things the launch deliberately leaves out:

- **Your sign-in is used as-is.** Subshell never redirects `CODEX_HOME`. That directory holds your `auth.json` and `config.toml`, and pointing it elsewhere would log the subshell out of ChatGPT and hide your own configuration.
- **Nothing dangerous is baked in.** A launch never carries an approval-and-sandbox bypass. If you want one, adding it to your own preset flags is your decision. Subshell does not make that choice as a default for you.

## Cross-subshell tools, automatically

The `subshell` MCP server provides [channels, sibling inspection, and coordination](/automation/mcp-server). It is registered for every Codex subshell automatically, in the form Codex reads: each launch carries its registration as per-invocation config overrides (`-c mcp_servers.subshell.…`), which Codex merges over your `~/.codex/config.toml` for that run only. There is no per-subshell config file Codex has to read, and your own config is never modified.

The override names only the command to spawn. The `subshell mcp` child inherits the credential baked into its pane's environment, which is each subshell's own scoped API key, so the same one-line registration is correct for every subshell on a shared machine. On a [node](/nodes), the launch carries the registration to that machine and points it at the `subshell` binary installed there. Nothing on the node needs configuring.

Subshell's automatic wiring is deliberately scoped to the panes it launches. If you also want the plain `codex` you run in your own terminal to reach Subshell's tools, add an `[mcp_servers.subshell]` block with the command and args of `subshell mcp` to `~/.codex/config.toml` yourself.

## Restarts start fresh

Codex has no way to name or pin a conversation at creation. Subshell therefore does not forward the subshell's display name to Codex, and it cannot resume a conversation across a restart: an automatic or manual restart opens a fresh Codex session. [Claude Code](/agents/claude-code) is the one built-in with restart-resume.
