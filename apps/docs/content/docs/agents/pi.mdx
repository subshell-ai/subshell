pi is the minimal, extensible agent harness from pi.dev. It deliberately has no built-in MCP support at all, so Subshell cannot register its [MCP server](/automation/mcp-server) automatically. Registration is a one-time, two-step setup that the [preset editor](/use/presets) shows you. Subshell keeps pi's minimalism intact: it drives the plain `pi` binary and adds only its own launch environment.

## Finding the binary

Subshell resolves `pi` on the machine that will run the pane. It first tries the `pi` on the PATH there, which includes what a login shell would find. It then checks its known install location under your home directory. Set `PI_PATH` on that machine's environment to name the binary explicitly.

If detection finds nothing, [Installing Agent CLIs](/agents/installing-agent-clis) covers the one-line installer, and the [vendor docs](https://pi.dev/docs) describe the manual path.

## What a launch looks like

A bare launch opens the pi TUI. The [preset editor](/use/presets) offers pi's per-invocation settings as fields (model, provider, thinking level), plus its suggested flags.

Besides Claude Code, pi is the one harness that lets you name its own session at creation, and Subshell does: a pi subshell's display name is forwarded as pi's session name.

## Registering Subshell once

MCP arrives in pi's world as an extension, so the setup is two labeled steps, both shown in the MCP section of the pi preset editor, both copy-paste ready:

1. **Install the adapter extension**: `pi install npm:pi-mcp-adapter`. This is the community extension that gives pi MCP support; it is what makes the second step readable.
2. **Register the `subshell` server**: the editor shows an `mcpServers` JSON snippet in the standard shape the adapter reads. Put it in `~/.config/mcp/mcp.json`, or a project's `.mcp.json` if you want it scoped to one repository.

The snippet names `subshell mcp` as a PATH command rather than one machine's absolute path, so the text you paste is correct on every machine that has the `subshell` agent installed. Every enrolled node has it, because that is its own daemon's binary. Run the steps **once on each machine where pi panes run**.

Until you register, pi subshells launch and run normally; you have no [channels](/use/channels) or agent-to-agent tools inside them.

> [!note] Why one registration is safe for every subshell
> The snippet names only how to start `subshell mcp`. The process inherits the environment of the pane that spawned it, including that subshell's own baked-in API key, so the single entry serves every pi subshell on the machine, and no pane can authenticate as another.
