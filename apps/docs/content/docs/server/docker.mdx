Run Subshell Server from the published image, or with the compose file the repository ships.

## The image

The image is packaging, not compiling. It carries the published, signature-verified `cli-server` release binary, the same artifact the install one-liner installs, on `debian:trixie-slim` together with tmux, Node 22, and the five harness CLIs (`claude`, `codex`, `opencode`, `hermes`, `pi`), so panes work on a fresh install. `subshell-server version` answers the same inside the container as outside it, and the server listens on port 3080 on all interfaces.

## First run

Everything persistent lives under `/data`, so the container needs exactly one volume:

```bash
docker run -d -p 3080:3080 -v subshell-data:/data ghcr.io/subshell-ai/subshell:latest
```

No environment is required. On a fresh volume the entrypoint runs `subshell-server init` and mints a unique `BETTER_AUTH_SECRET` into `/data/config.env` at `0600`, so each install signs its own sessions, and the file stays on the volume through every later update. The image sets `NODE_ENV=production`, where a boot would refuse to run on the public placeholder secret; the per-install minting is what a fresh container does instead. Pass `APP_BASE_URL` when people open the instance at a URL other than the host address, as covered on [Networking and addresses](/server/networking). Then open the address and create the admin account.

> [!warning] Create the admin account promptly
> The setup endpoints are public until the first account exists, and that is what lets you create it. On a LAN, the first browser through becomes the admin. The window closes when the first account exists.

## Updating

The image is the unit of update. Pull the new image and recreate the container; the published tags are `latest` and the version of each server release:

```bash
docker pull ghcr.io/subshell-ai/subshell:latest
docker rm -f <name>
docker run -d -p 3080:3080 -v subshell-data:/data ghcr.io/subshell-ai/subshell:latest
```

The dashboard's update refuses on a containerized install and says exactly this: the image is the unit of update, pull and recreate. `subshell-server update --check` inside the container prints the same answer, and [Update the server](/server/updating) carries the full story of why.

What survives the recreate follows the volume: the database, browser sessions, settings, and the minted secret continue unchanged. Running subshells do not: the container owns its tmux server, and tmux state is process state, so a recreate ends every running pane. The rows surface as dead and you restart them from the UI. On a Proxmox host the same pull-and-recreate runs with a rollback if the new container fails its health check, on [Install on Proxmox](/server/proxmox).

## The compose rail

[docker-compose.yaml](https://github.com/subshell-ai/subshell/blob/main/docker-compose.yaml) pulls this same image, so `docker compose up -d` gives the identical server with your host's files wired in. The file's header comment describes building the image locally from a staged release binary instead. One file must exist before the first up: `docker/gitconfig`. It is a bind-mount source, and Docker silently creates a missing source as an empty directory. Copy the example and set your commit identity; ssh-format signing uses the `ssh` binary in the image, and the host's `~/.gitconfig` is deliberately not used because an external signing program configured there does not exist inside the image.

The harness CLIs are baked into the image, and the compose mounts override them with host binaries and state when that is what you want. The mounts are:

| Mount | Host side | Why |
|---|---|---|
| `/data` | `~/.config/subshell-server` (`SUBSHELL_DATA_HOST_DIR`) | Database, pane logs, channel keypairs, `config.env`: everything that must survive. |
| your projects | `~/projects` at its real path (`PROJECTS_DIR`) | Stored working-directory paths in the database resolve unchanged inside the container. |
| `claude` binary | `CLAUDE_BIN`, read-only | Overrides the harness CLI the image bakes; adjust these three mounts for a different harness. |
| `~/.claude`, `~/.claude.json` | read-write | Where the harness keeps its session records. |
| `~/.ssh` | read-only, plus `docker/ssh-config` over `config` | Git push and signed commits from panes. |
| `docker/gitconfig` | read-only | Commit identity, as above. |

Three details that were measured in the field rather than assumed:

- **The container runs as your host uid** (`user:` from `$UID:$GID`), so SQLite files, logs, and harness edits on the bind mounts keep sane ownership with no fixups.
- **Harness and SSH state mount at the container's home** (`/home/subshell`), not at your host paths. The image pins `HOME` there because the numeric uid has no passwd entry, and panes inherit it. Mounting at the host spelling instead leaves every pane reading an empty directory.
- **Any harness pane can read the mounted SSH keys.** This is deliberate on the same trusted-host posture as everything else here, not an oversight. Decide it before enrolling this machine to a shared instance.

`3080:3080` is published, not loopback-bound: remote access runs through a reverse proxy that connects to this host's reachable IP, and a `127.0.0.1` publish makes every proxied request a 502. `APP_BASE_URL` (from `.env`, or `-e` on a plain `docker run`) should be the URL people actually open, with any other names they browse on added as trusted origins; a container is no exception. `restart: unless-stopped` brings the compose service back with the Docker daemon, which assumes the daemon itself is enabled. Firewall and port specifics are on [Ports and firewalls](/reference/ports).

To move an existing host-run instance in, stop the old server and copy the database and the pane-log directory into the host directory that will mount at `/data`. Bring the old instance's `config.env` (or its `BETTER_AUTH_SECRET` line) along too: the same secret is what lets existing browser sessions continue on the container, and a supplied value is persisted verbatim. New `ssh` hosts need an `ssh-keyscan` on the host first, since the mounted `known_hosts` is all the container trusts.

Two file-level details: after editing `docker/gitconfig`, recreate the container. A single-file bind mount pins the inode, so edits to the file never arrive. Host-specific extras (a `gh` config, say) belong in `docker-compose.override.yaml` beside the base file: it is gitignored and merged automatically by every `docker compose` command.
