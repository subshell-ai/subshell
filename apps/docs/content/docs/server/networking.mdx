Control which addresses your control plane answers on and which browsers may sign in from them.

Three settings decide this, and they are easy to conflate. Once you separate them, the common sign-in failure becomes a one-field fix.

| Setting | Question it answers | Default |
|---|---|---|
| `HOST` | which network interfaces does the server listen on? | `0.0.0.0`: all of them |
| `APP_BASE_URL` | what address does the instance call itself? Auth redirects use it, and it is trusted automatically. | `http://localhost:<port>` |
| `TRUSTED_ORIGINS` | what other addresses may a browser sign in from? | the two dev-server ports a source checkout uses |

The bind is the network fact: `0.0.0.0` (the default since 2026-09-08) means remote nodes and devices can reach the server. `HOST=127.0.0.1` in `config.env` restores loopback-only. The other two are identity facts: which name the instance vouches for, and which names its browsers may use. A wildcard bind is a listen address, not an identity. The string `0.0.0.0` never joins the trusted list; what binding on it does is make the machine's own LAN addresses relevant, as described below.

## What a browser may use

Every sign-in carries the browser's `Origin`, and the instance keeps an allowlist of origins it will accept it from. The list is assembled live, per request, from four sources: the instance's own origins (both loopback spellings of the port, plus the base URL's origin, plus `http://<host>:<port>` when `HOST` names a concrete address), this machine's own LAN addresses on a wildcard bind, your `TRUSTED_ORIGINS` extras, and the addresses each enabled [network plugin](/server/network-plugins) reports for this host. A phone on your Wi-Fi signs in at the server's LAN address with nothing to configure, because the machine's interface addresses are derived from the kernel and trusted automatically (since 2026-09-17).

What is deliberately missing is a fifth source: the request itself. The list is never derived from the request's `Host` header. "Trust the origin that matches the host you dialed" is precisely the DNS-rebinding hole the allowlist exists to close. The full derivation, source by source, and the mechanics behind the live per-request read are on [Security model](/concepts/security-model).

## Fixing 403 "Invalid origin"

This is the symptom everything above is designed to produce when an address is not on the list. It is unhelpful on its own because it names no key. The classic case, a phone on the Wi-Fi dialing the server's LAN IP while only loopback was trusted, stopped being possible in 2026-09-17, when the machine's own addresses became derived automatically. What still produces the error is a name. The server answers on `http://box.local:3080` and the app renders, but a `.local` host, a DNS entry, or any other name that is not one of the machine's interface addresses sends an `Origin` nothing matches, and sign-in fails. The server is not broken; it is refusing an address it was never told about. Production enforces this strictly, which is where you will meet it.

1. Name the address you actually browse from, with the CLI:

   ```bash
   subshell-server configure --trusted-origins http://box.local:3080
   subshell-server service restart
   ```

2. Or edit the same field on Settings → Networking, where a change needs no restart: the origins list is re-read live, so the retry works from the page you fixed it on.

Two rules pick the right lever:

- "Also reachable at" → add an origin. Nothing else moves.
- "This is the address now" → change `APP_BASE_URL`, and restart. Read the next section first.

`init` still warns at write time when a LAN bind will refuse names, printing the exact command. The addresses the machine holds itself are no longer part of what you must say.

> [!important] Changing the base URL moves your passkeys
> `APP_BASE_URL` is also the passkey rpID: passkeys are bound to the host they were minted for. Change it and existing passkeys stop working on the old address, the Subshell Server desktop window (which opens on loopback) included. Adding a name to `TRUSTED_ORIGINS` has no such effect, and is the correct lever when the goal is *also*.

## What the list will not accept

An entry is a scheme, host, and optional port, and nothing else: paths, queries, fragments, and credentials are refused, and wildcards are refused too, because a written `https://*` would match every https origin. Both writers of the list validate and store the canonical spelling a browser sends, so the notation you type works. An operator who genuinely wants a pattern can still set the env var or hand-edit `config.env`, which bypass the validators by design; `subshell-server status` then reports per-entry problems. [Security model](/concepts/security-model) carries the mechanics and the derivation rule; the [threat model](https://github.com/subshell-ai/subshell/blob/main/docs/security.md#8-network-boundary) accounts for what the allowlist defends.

## Reaching the box from anywhere

The posture is a trusted network, so no TLS is enforced. For operation from beyond the LAN, we recommend bringing the network to the box (WireGuard, Tailscale, an SSH tunnel) rather than the box to the internet. That is exactly what the [network plugins](/server/network-plugins) automate: joining Tailscale, Headscale, or NetBird and publishing Subshell on the mesh. There, the plugin's own record makes the new address trusted; nothing is unioned into `TRUSTED_ORIGINS`, and unpublishing forgets it. Cloudflare Tunnel is the one deliberate public exception, and it refuses to publish until an Access application guards the hostname. Every address carries a `secureContext` flag, which is a statement about the browser (passkeys and secure cookies need https or loopback), not about encryption: a WireGuard mesh encrypts plain `http://` end to end, and passkeys still won't work on it.

Firewall and port specifics are on [Ports and firewalls](/reference/ports); the enforcement-point-by-enforcement-point accounting lives in the threat model.
