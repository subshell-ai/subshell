In Subshell, the word **server** names exactly one thing: the control plane.

## One process, one port

The control plane is the API, its SQLite database, and the web UI it serves, running as one process on one port (default `3080`). A single `subshell-server` process answers:

- the REST API under `/api`, and the WebSocket used to attach to live panes;
- the web UI: the SPA is embedded in the published binary, so the host needs no separate frontend install;
- `/docs`, the OpenAPI page generated from the routes;
- the node binaries and install script that enrolled machines download.

The published form is one self-contained binary per platform (`linux-x64`, `linux-arm64`, `darwin-arm64`, and `darwin-x64` for Intel Macs). It needs no Bun, no checkout, and no runtime download to boot. A machine outside these targets is refused by name, never silently mis-resolved.

## The words around it

"Server" does not mean a machine that runs agents. That word is [node](/nodes): the `subshell` daemon on any machine that hosts subshell panes. Your control-plane host usually runs agents too, but it is then doing both jobs, and the docs keep the roles apart. Its row in the Nodes list is named by an admin and defaults to "Server". Underneath, it is the `local` node, launched through the same tmux machinery as any other.

## Where its state lives

A running instance keeps its on-disk state in two places. The config home at `~/.config/subshell-server` holds the `config.env` file and the generated auth secret. The data directory holds the database, pane logs, channel keypairs, node signing keys, downloaded node binaries, installed plugins, database backups, and the server's own log. `subshell-server status` prints every one of those paths, and [Files and paths](/reference/files-and-paths) maps them in full.

## Who decides what

You manage the control plane from three surfaces, and each owns a different kind of decision:

| Surface | Owns |
|---|---|
| The dashboard (Settings pages in the web UI the server serves) | Everything about a running instance: users and roles, registration, plugins, nodes, agent CLIs, API keys, and Settings → Service, Networking, Logs and Updates: the process, the addresses, both log tails, and versions. |
| The `subshell-server` CLI (on the control-plane host) | Everything that must work when the server is not running: `init`, `configure`, `service`, `status`, `update`, `backup`. |
| `config.env` (the file both of the above write through) | Keys no tool owns, and the escape hatch when a validator refuses something you genuinely mean. |

The line between the first two follows one rule: if an act leaves the server unreachable, it cannot be driven from a page the server serves. So over HTTP an admin can change the address settings, restart the process, arm or disarm start-at-login, read logs, and trigger an update. The restart is available only when the service manager reports this very pid; a hand-run server refuses it. The verbs `stop`, `start`, `service install`, and `service uninstall` have no route by design, and neither does the reset. Each one takes down the page you would click it from, so they stay CLI verbs. The reset is deliberately off the network entirely, and lives in the Subshell Server desktop assistant, described on [Reset](/server/reset).

The Subshell Server desktop app adds no management surface of its own. It wraps the same CLI for the moments when no server is running: first run, recovery, update, and reset. Everything about a live instance stays in the dashboard, where a browser on the LAN and a headless install can both reach it.
