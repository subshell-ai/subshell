title: Audit Log
description: "The instance's record of consequential acts, such as installs, role changes, restarts, and repoints, and what each row names."
---

The audit trail answers who did what to your instance, and when. Every consequential act writes a row containing **who** (the admin's user id, or `null` when the server itself acted), **what** (a machine-readable action name like `user.role_change`), **to which target** (its kind and id), **context** (per-action metadata), and **when**. Writing is best-effort by design: if the audit insert itself fails, the act it describes still completes. A logging problem never undoes or blocks an operator's action.

## Reading the audit log

- **Settings → Logs → Audit tab**: a read-only trail of every recorded event, newest first, paged 25 at a time and walkable to its beginning. Each row shows when, action, target, and context. Refreshing is reopening.
- `GET /api/audit?limit=25`: the same rows as JSON, for an admin cookie session (up to 500 per page). For older pages, pass the last row of the page above as `beforeCreatedAt` and `beforeId`.

## What is recorded

Not every request, only acts. The families:

- **People.** Accounts created, role changes (with the before and after), password resets, and disable or enable. A password reset records that it happened and how many sessions it cut, never the password, in any form. Approval-queue decisions carry their own rows: approve and reject each name the arriving account and which provider it came through.
- **The instance's own switches.** Flips of registration (the trail still spells this by its old settings key, even though the answer now lives on the E-mail provider's row), of node-enrollment permission, of the instance display name, and of debug logging. Each is audited only on a real change, with the old and new values, so the log reconstructs decisions rather than page visits.
- **Sign-in providers.** Creates, updates (which fields moved, and the issuer), and removals. The client secret is never recorded. See [Sign-in Providers](/server/sign-in-providers).
- **Credentials.** System API keys created, enabled, disabled, and deleted; node setup keys created and revoked. Plaintext never appears: setup-key rows name the key's id and nothing else. An admin revoking someone else's key is the one row in that family with context: `{ foreign: true, ownerUserId }`, so the trail records whose key the admin revoked. Ids, never the key text.
- **Subshell lifecycle.** Create, restart, terminate, delete.
- **Nodes.** Enroll, delete, rename, key rotation, directory-allowlist changes, share changes, service verbs (start, stop, restart, install, uninstall, with whether `force` was used), repointing to another control plane (the row names the new address, which is the disclosure the act makes), logging toggles, maintenance flips, and binary updates. A maintenance row can carry a `null` actor: that is the machine's own `subshell maintenance on|off`.
- **The server, to itself.** Config writes (key, old value, new value; this surface cannot write secrets), restarts, autostart armed or disarmed, and supervision switches. The supervision row is the least strict of these: it is posted by the desktop app itself as a record of intent, so the sanctioned path always leaves one and a direct command invocation would leave none. Updates are recorded twice: once when an admin presses the button (actor: the admin) and once at the completing boot (actor: `null`). A job that dies mid-download still leaves the first half.
- **Break-glass.** A recovery login that rewrote an admin's credential is audited as such, alongside the banner every signed-in user sees.
- **Plugins and networks.** Installs, enables, disables, and uninstalls; and for network plugins: configure (field names only, never the secret values), install, join (mode and outcome, never the credential used), publish, unpublish, and leave (the rows name the affected origins).
- **Software installed on this host on request.** An agent CLI's installer run, and a tmux install. Both are admin acts that put code on the control-plane host, and both are audited.

## What is not recorded

- **Reads and re-checks.** Nothing that changes state earns a row. That includes the Updates page's Re-check button, so the `server.update` rows stay easy to find.
- **Request lines.** Those belong to the log file, not this table (see [Logs & Debugging](/server/logs-debug)). Even there they stay off unless debug logging is explicitly on.
- **Secret values.** This is the row-writing discipline behind the whole table: rows name origins, keys, field names, counts, and before/after values for things that are not credentials, never a password, a token, or a secret. It is what makes the audit trail safe to screenshot, paste into an issue, or hand to whoever is helping you debug.
