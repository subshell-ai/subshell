# apps/website

The public marketing site at subshell.sh. Static export (`next build` → `out/`),
deployed by `website.yml` as an assets-only Cloudflare Worker. Like `apps/docs`,
it is a site, not one of server/node/client, which is why it sits directly under
`apps/`.

- The install section renders ONLY from `releases.json` (repo root, generated by
  `scripts/site-releases.ts`). Never hardcode a version or an artifact filename.
- The Mac arch menu (Apple silicon / Intel) is capability-driven, never
  version-driven: `scripts/site-releases.ts` attaches each desktop entry's
  verified `desktopAssets` (read from the release's OWN `release-manifest.json`,
  signature checked against the committed publisher key, the same rule every
  update path follows), and `lib/install.ts` offers Intel only when that list
  names the derived `-darwin-x64.dmg`. No probe data ⇒ no menu, plain button.
  `--check` never fetches and strips the field from the comparison.
- `data/releases.json` is build input (gitignored), copied from the root file by
  `bun run copy-releases` before build/dev. The same step copies the root
  `install-server.sh` / `install-client.sh` into `public/` (also gitignored):
  the install one-liners fetch from `SITE_ORIGIN` (`lib/site.ts`, the one
  spelling of the site's origin) and the site serves its own copies. Editing a
  root script therefore means a `website.yml` dispatch, or the published
  one-liner serves stale bytes - the rule and the tripwire are in
  `docs/release-and-ci.md`.
- The palette in `app/globals.css` is the MARKETING token set, deliberately not
  the SPA design system; `lint:design` does not scan this app.
- Apply the shared content guide to routine copy edits. Ask Theo when wording would change product meaning or positioning.

For a private dev proxy, set `WEBSITE_DEV_ORIGINS` to comma-separated hostnames
in the gitignored `.env.local`, then restart the dev server. This allows Next.js
to establish its development connection through those hosts. Never commit private hostnames.

## Product demonstration clips

### Editorial expectations

These are standing user preferences, established during the October 19, 2026
media refresh. Apply them to future recordings as well as this demo.

- Show an interactive agent running inside a subshell and doing a useful,
  concrete task. Give the viewer a clear request, visible work, and a result
  they can understand, such as a feature implemented and its tests passing.
  Trivial one-sentence prompts, explanations of sample code, and terminal
  sessions merely named after agents don't demonstrate this workflow.
- Create multiple subshells in one workspace. Switch between that workspace's
  tabs to show related work, such as implementation and tests. Don't switch
  between the Workspaces and Subshells sidebar sections or visit the dashboard
  during the clip.
- Keep the phone sidebar closed. Keep the desktop workspace sidebar visible, including its bottom navigation
  bar. For a clip demonstrating subagents, show its compact
  parent arrow and connected child branches. Preserve the tab
  strip so the relationship between the subshells stays clear.
- Use real agent execution and real output. Trim idle waits, but preserve the
  sequence of request, work, and result. Don't substitute scripted responses,
  fabricated notifications, or unrelated output to make the recording busier.
- Record the current built UI. Refresh the website videos and posters, README
  animation, and affected documentation screenshots together. Captions must
  describe the workflow actually shown.
- Watch each complete clip at its displayed desktop and phone sizes before
  calling it finished. Check that the task makes sense, text is readable,
  terminal padding is intact, controls aren't clipped, and the result stays
  visible long enough to read. Passing playback checks alone isn't enough. Judge text size in the embedded
  player, not in a full-resolution frame: a large desktop viewport can shrink
  otherwise readable text into tiny lettering on the website.

The task-summary example below is one acceptable scenario, not a requirement
to reuse that exact task forever. A replacement should tell an equally clear
story about doing real work with an agent in Subshell.

### Capture and playback

`components/product-demo.tsx` replaces the phone and desktop screenshots with
short, silent recordings of a real task on an isolated demo server.
Mobile shows browser/PWA access, not the native mobile app. Keep recordings at
fixed viewport sizes and use sample projects and accounts without credentials
or personal content.

Assets live under `public/demos/`: both use H.264 MP4 because it is smaller
than VP9 WebM at the selected quality. Both have WebP
posters. Encode without audio at 15 fps, preserve terminal legibility, and use
MP4 fast-start metadata. Current viewport sizes are 390×844 and 900×560, captured at 2× pixel density
(780×1688 and 1800×1120 encoded frames). The phone clip shows an interactive Codex subshell implementing a task summary
feature and a second subshell running its tests. The desktop clip delegates
implementation and tests to two real Codex subagents, demonstrates collapsing
and expanding them with the parent arrow and active parent row, then runs the
tests in the second subshell. Stay in the same workspace throughout: switch tabs, never sidebar
sections. Keep the phone sidebar closed and preserve the visible tab strip.
The desktop clip also drags the test subshell into the lower Subshells section
and back into the workspace, holding each centered drop hint long enough to
read. The same running session returns as a tab.
Generate them with `bun e2e/capture-product-demo.ts` after building the SPA.
The capture requires an authenticated Codex CLI. It uses sample files in a
temporary project and an isolated server, lets the agent edit those files and
run tests, and trims idle waiting time. Never fabricate terminal output or add
a notification that the recorded workflow doesn't produce.
The root README uses an optimized animated GIF linked to the full-quality MP4
because GitHub strips repository-hosted HTML video elements.
Terminal font sizes are 20px in the desktop subagent clip and 18px on mobile. The desktop capture
uses a compact viewport so the text stays large when embedded in the page;
higher recording resolution alone does not make text more legible. Use
`bun e2e/capture-product-demo.ts --subagents` to refresh only the desktop
clip, its poster, and the README animation.
Use `--mobile-only` to refresh the phone clip without replacing the desktop
subagent demonstration. The sidebar has one workspace panel with a lower
Subshells section and a bottom navigation bar; there is no mini rail or desktop panel collapse.
Inspect frames for layout changes before encoding; changing viewport during a
recording is not an acceptable device transition.

The player attaches sources only when visible, pauses offscreen and when the
document is hidden, and shows posters until explicit playback for data-saving preferences.
Silent product clips autoplay even with reduced motion enabled. The video itself is a keyboard-accessible toggle;
do not add visible Play/Pause links beneath it.
Verify duration, stream metadata, export assets, responsive layout, playback,
manual pause/resume, and preference handling after replacing clips.

## Website copy

Use the shared [content guide](../docs/STYLE.md#product-copy-and-confirmations)
for wording decisions. Keep action headings fixed and put variable details in
the body. Describe verified capabilities and ask about positioning when a
copy change would alter the product promise.

Follow [the repository's writing voice](../../AGENTS.md#writing-voice). Write
as you'd speak to a peer, using active verbs and natural contractions. Vary
sentence structure and connect ideas so the text flows. Avoid textbook
formality, stock marketing or AI phrases, and repetitive closing summaries.

Use plain, concise language and consistent product terms: Server, Client, node,
agent, and subshell. Introduce a subshell as a terminal session running an agent
or a shell; “session” is fine in explanations after that. Introduce a node as
a machine that runs agents. Use “your
server” and “dashboard” in visitor-facing instructions rather than “control
plane”. Describe what an installation does; keep digest algorithms, binary
paths, and other implementation details in documentation. Both installation
choices use “or the CLI” above their terminal installation command. The client
command installs the desktop app, including its bundled node; headless node
setup uses a command and setup key from the server dashboard. Use sentence case, the serial comma,
and descriptive captions that do not require knowing abbreviations such as PWA.
