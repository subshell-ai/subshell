# 1.0.0 Launch Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Mark every published component 1.0.0 (or its next major if past 1.0), cut the four GitHub Releases and eleven npm packages at those versions, and refresh the live surfaces.

**Architecture:** Pure release mechanics. Three major changesets ride the changesets Action into version PR #168; the merge publishes npm; one `release.yml -f app=all` dispatch cuts the binaries. No code changes anywhere.

**Tech Stack:** changesets, bun, GitHub Actions (`release.yml`, `website.yml`), `gh` CLI, `scripts/site-releases.ts`.

**Spec:** `docs/superpowers/specs/2026-09-25-1.0.0-launch-design.md`

## Global Constraints

- Never hand-cut a release tag. The four `*-v*` tags belong to `release.yml`; the eleven `<pkg>@*` tags to `npm-publish`.
- Never `gh pr merge --auto`: it merges immediately in this repo, not wait-for-green. Every merge is explicit and watched.
- Shipped prose carries no em dashes (U+2014). Changeset summaries go into CHANGELOGs and release bodies.
- No new changeset may name an ignored package (`.changeset/config.json`); every target here is versionable.
- Two operator checkpoints gate outward steps: **Checkpoint 1** before merging #168 (Task 4), **Checkpoint 2** before touching the live instance (Task 8). Do not pass either without an explicit "go" from the operator.
- `@internal/docs` and `@internal/website` are NOT marked 1.0.0; they move on their pre-existing pending bumps only.
- Target table (verbatim from spec): `@internal/server` 0.17.1→1.0.0, `@internal/node` 0.17.0→1.0.0, `@internal/desktop-server` 0.15.0→1.0.0, `@internal/desktop-client` 0.12.0→1.0.0, `@subshell-ai/plugin-{codex,hermes,opencode,pi,terminal,cloudflare-tunnel,headscale,netbird,tailscale}` 0.1.2-0.2.0→1.0.0, `@subshell-ai/plugin-api` 2.1.2→3.0.0, `@subshell-ai/plugin-claude-code` 2.0.0→3.0.0. Pre-existing pendings ride along untouched: `@internal/docs` 0.3.2→0.4.0, `@internal/website` 0.0.1→0.1.0.

### Task 4: The cut

**Files:** none (CI's).

**Interfaces:**
- Consumes: main at 1.0.0 for all four apps (Task 3).
- Produces: four GitHub Releases with signed manifests; `release.yml`'s final job commits the refreshed `releases.json` naming all four at 1.0.0.

- [ ] **Step 1: Confirm no cut is in flight, then dispatch**

```bash
gh run list --workflow .github/workflows/release.yml --limit 1 --json status,displayTitle
gh workflow run release.yml -f app=all
```

Expected: the newest run is a completed push-event; the dispatch is accepted. `gh run list --workflow .github/workflows/release.yml --limit 1` then shows the queued `Release` (workflow_dispatch).

- [ ] **Step 2: Watch to green (about an hour)**

```bash
gh run watch <dispatch-run-id>
```

Expected: plan pushes exactly the four tags `cli-server-v1.0.0 cli-node-v1.0.0 desktop-server-v1.0.0 desktop-client-v1.0.0`; every build/publish/publish-releases job concludes success. Any failed shard publishes nothing: re-dispatch the same way to complete the half-cut (never delete the tag without the release).

- [ ] **Step 3: Verify the four releases and their assets**

```bash
for t in cli-server cli-node desktop-server desktop-client; do
  gh release view "$t-v1.0.0" --json tagName,name,isLatest,assets \
    --jq '{tag:.tagName, latest:.isLatest, assets:[.assets[].name]}'
done
```

Expected per component: the binaries/bundles + `.sha256` + `release-manifest.json` + `release-manifest.json.sig`; desktops additionally the updater package and `latest.json`. Do not assert on `isLatest` (its meaning across component prefixes is the updater's job, not this check's); assert instead that each release body reads like its CHANGELOG's 1.0.0 section: `gh release view cli-server-v1.0.0 --json body --jq .body | grep -c "1\\.0\\.0"` is ≥ 1.

- [ ] **Step 4: Verify the cut refreshed releases.json**

```bash
git pull --ff-only origin main
bun scripts/site-releases.ts --check
grep -o '"version": "1.0.0"' releases.json | wc -l
```

Expected: `--check` exits 0; the count is 4 (all components at 1.0.0). If the refresh commit is missing, check the cut run's final job before moving on; it is part of the cut, not a separate dispatch.
