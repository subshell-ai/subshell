# Nodes Implementation Plan

**Spec:** `docs/superpowers/specs/2026-08-31-nodes-design.md` (cite as "spec 2026-08-31 §N" in code comments, per repo idiom)

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking. Phases are strictly ordered; **within** a phase the tracks run in parallel by different agents against the frozen contracts — do not edit a frozen file's contract without all tracks' owners agreeing.

**Goal:** Let any user register a Linux/macOS machine as a **node** (setup key → `mote-agent` enroll → outbound signed-command websocket) and run sessions there with full parity to the control-plane host, which itself becomes the seeded `local` node.

**Architecture:** Four artifacts carry the whole design: (1) the **node wire contract** in `@internal/session-protocol` (`node-frames.ts` + `node-signing.ts`) — signed command envelopes (ES256 JWS, aud-bound, seq+jti replay defense) and unsigned agent events; (2) the **`NodeLauncher` seam** in the backend — `LocalLauncher` (today's tmux/fs code verbatim) vs `RemoteLauncher` (commands over a per-node RPC map), so `SessionManagerService` and `ws/session-ws.ts` gain one branch point instead of a fork; (3) the **nodes data plane** — `nodes`/`node_shares`/`node_setup_keys`/`node_harnesses` tables + `node-access.ts` cloned from the session-sharing access resolver + a `kind:"node"` api key that is rejected on all REST and only ever authenticates `/ws/node`; (4) **`apps/agent`** — a `bun build --compile`d daemon importing `@internal/harnesses` (so harness detection/resume/launch-assembly is literally the same plugin code on both sides).

**Tech Stack:** Bun, Elysia, Kysely + bun:sqlite, better-auth api-key, jose (JWS signing), LogLayer, React + TanStack Query, Playwright (e2e), `bun test`.

## Global Constraints

- Verification after **every** task: `bun run verify-types`, `bun run lint:check`, `bun run test` from the repo root, all green before committing. Backend route/schema changes need `turbo build` so `@internal/backend-client` re-infers (`build.md`).
- Migration `0017-nodes.ts` lives in `apps/backend/src/db/migrations/` **and** in the static provider map in `db/migrate.ts` (file name == map key). No dynamic imports anywhere — especially in `apps/agent/src/main.ts`'s import graph (`bun build --compile`).
- New `api/nodes/` module mounts into `computeRoutes` in `api/routes.ts`; if `verify-types` trips TS2589, rebalance the sub-aggregates (move `filesRoutes` → `coreRoutes`) — grouping is behavior-neutral.
- Elysia `t` schema: every property carries a `description`; every endpoint an `operationId` + tags; errors are `"ApiErrorResponse"`. JSDoc on public functions and interface props.
- Invisible nodes answer **404**, not 403; insufficient access answers **403** (session rule, spec §2).
- Node share capabilities (spec §2): **any share level grants launch**; `edit` additionally grants node config (harness toggles, Re-check). `local`'s seeded Everyone/edit share row **is** the admin's launch switch — no settings flag exists.
- Node-key semantics: `deriveFromApiKey` grows an explicit named rejection of `metadata.kind === "node"` — node keys NEVER act on `/api/*` REST (spec §5.5).
- The browser `/ws` terminal contract is **byte-identical** for remote sessions (frames, `stripSyncMarkers`, replay-from-zero) — frontend/mobile change nothing for terminals (spec §6.5).
- `apps/agent` tests must never touch `~/.config`: a test preload points `MOTE_AGENT_HOME` at a temp dir (mirrors `test-preload.ts`).
- Pinned deps only (`.claude/rules/dependencies.md`); syncpack-clean: `jose` at `6.2.9` everywhere.
- Frozen during phase 1–2: `node-frames.ts` payloads, migration 0017, `NodeLauncher` signatures, the REST table in spec §9. Additive changes OK with a version note; breaking changes need all track owners.

## Parallelism & dependency contract

- Phase 0 is sequential and alone; 0.2→0.3→0.4→0.5 are independent of each other and could internally parallelize (protocol / schema / harnesses / refactor touch disjoint files).
- Phase 1: **1B depends only on freeze A–D** (its counterpart is the enroll/ws contract; unit-testable with a self-signed envelope); **1C depends only on freeze E** (build blind against `/docs`, integrate at phase end); **1A owns every frozen file this phase**.
- Phase 2: 2A ↔ 2B are lock-step on the command set; the phase-1 `result:"unsupported"` skeleton lets each side integrate against a partially-built other side. 2C trails both.
- Integration seams to re-check at each phase boundary: enroll response shape, `ready` capability strings, `NodeLauncher` signatures, `nodeId` in session views.
