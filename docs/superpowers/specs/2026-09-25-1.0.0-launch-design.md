# Mark every release 1.0.0

Date: 2026-09-25
Status: approved, pending implementation plan
Owner: operator ruling 2026-09-25 ("subshell is now in a great state")

## Goal

Declare the product line stable: every component the release machinery
publishes moves onto a deliberate, human-meaningful version in one wave. Not a
feature change. A versioning milestone, executed entirely through the existing
changesets and `release.yml` machinery, with no hand-cut tags.

## Scope: which versions, and why each lands where

The four GitHub Release components and the eleven `@subshell-ai/*` npm packages
are the release surface. Docs and website name none of the vocabulary and ride
their own tag/workflow; they are not marked 1.0.0 (see §Website below for the
one website change this launch does require, and why it is not a 1.0 marker).

Three rules decide every package's target:

- **0.x forward major = exactly 1.0.0.** `semver.inc("0.x", "major")` is
  `1.0.0`, so a `major` changeset lands a pre-1.0 package on 1.0.0 by semver,
  not by a hand-typed number. Every 0.x installed build reads 1.0.0 as a normal
  upgrade.
- **Already past 1.0 keeps its own line and takes the next major.** A package
  that is already past the 1.0 mark cannot be "marked 1.0.0" without a
  downgrade, so a major bump moves it to its own next major. Operator: "if
  it's past it, then just bump to next major."
- **Highest bump wins.** The 38 pending changesets are minor/patch; a `major`
  on the same package dominates them. Both note sets fold into the one new
  CHANGELOG section.

## A stale gate this launch first clears

`releases.json` (root) is what the marketing site reads to name the latest of
each component. The `releases.json pipeline` landed in #162 *after* the 0.17.x /
0.15.1 cuts, so those cuts never refreshed it and `bun scripts/site-releases.ts
--check` has been failing in `lint.yml` on every push since. It is a stale
generated file, not a broken pipeline. The prep PR regenerates it first
(`bun scripts/site-releases.ts`, commit), which un-reds main immediately; the
cut's own final job then regenerates it again from the new 1.0.0 tags.

## The one website change, and why it is not a 1.0 marker

`website.yml` refuses to redeploy when `website-v<version>` is already
published at another commit ("delete the tag to re-cut"). So shipping the
fresh `releases.json` to subshell.sh needs the website's version to move.
No new changeset is needed: the pending `quiet-otters-ship.md` minor already
moves `@internal/website` 0.0.1 → 0.1.0 in the same version PR. The tag
moves with it, and website.yml deploys cleanly. This is a tag-move, not a
1.0 marking; docs is left alone entirely.

## Process: five steps, two checkpoints

Everything up to merging the version PR is inert and revertable. The two
checkpoints are the operator's go/no-go gates.

1. **Prep PR to main.** One PR carrying: the regenerated `releases.json`; the 15
   major changesets, grouped into three files so each CHANGELOG bullet reads
   true for its audience (the four apps; the nine sub-1.0 plugins; the two
   past-1.0 packages). No website changeset is added; its pending minor
   already moves the tag. Landing it triggers
   the changesets Action, which recomputes version PR #168 to show every package
   at exactly its target, with all accumulated notes folded in and `bun.lock`
   resynced by the PR's own `lint:lockfile:fix` step.

2. **Checkpoint 1 (operator).** Verify #168's recomputed diff: 13 packages at
   1.0.0, 2 at 3.0.0, website at 0.1.0 and docs at 0.4.0 from their
   pre-existing pendings; CHANGELOGs carry the notes; `bun.lock`
   agrees. Show the version table; await go.

3. **Merge #168.** Version commits land on main. `npm-publish` self-gates on
   `needs_publish` AND `NPM_PUBLISH_ENABLED` (currently `true`) and ships the
   eleven `@subshell-ai/*` packages plus their `<pkg>@<version>` tags and
   per-package GitHub Releases. Watch to green.

4. **Cut.** `gh workflow run release.yml -f app=all`, version blank (read from
   package.json = 1.0.0). Plan pushes the four `*-v1.0.0` tags, build shards run
   on hosted runners, the publish job creates the four GitHub Releases with
   CHANGELOG-sliced bodies, signed `release-manifest.json(.sig)`, desktop
   bundles notarized and stapled, and `latest.json`. The cut's final job commits
   the fresh `releases.json` (all four components at 1.0.0). Any failed shard
   publishes nothing; re-dispatch completes a half-cut.

5. **Post-cut verification + live update.** `bash
   scripts/cli-e2e/published-release.sh` drives the real published releases.
   Dispatch `website.yml` (deploys with 1.0.0 baked in). Then, at **Checkpoint 2
   (operator)**, update the live `:3080` instance and the enrolled node to 1.0.0
   through the normal signed-manifest update path.

## Never / guards inherited from the release machinery

- **Never hand-cut tags.** The four `*-v1.0.0` and the eleven `<pkg>@` tags are
  workflow-owned.
- **Never write a changeset for an ignored package.** All 15 targets are
  versionable (four apps are private-but-versioned; eleven are publishable);
  none is in `.changeset/config.json`'s ignore list. Verified.
- **Desktop re-ships its CLI.** Each desktop bundle wraps its CLI built from the
  same commit, which is why step 4 is `app=all`: a server- or node-only fix
  reaches desktop users only through the matching desktop cut.
- **No auto-merge.** `gh pr merge --auto` merges immediately in this repo, not
  wait-for-green. Steps 3 and 4 are explicit and watched.

## Success criteria

- Four GitHub Releases `cli-server-v1.0.0`, `cli-node-v1.0.0`,
  `desktop-server-v1.0.0`, `desktop-client-v1.0.0`, each with signed manifest.
- Eleven `@subshell-ai/*` packages at their targets on npm with provenance.
- `releases.json` on main shows all four components at 1.0.0; the lint gate is
  green.
- subshell.sh serves the 1.0.0 download copy; live instance and node run 1.0.0.

## Out of scope

- Any behavior/feature change. This is versioning only.
- Marking `@internal/docs` or the website as 1.0.0.
- Renaming any tag prefix, package name, or component id.
