# SSH sealed agent relay (Milestone 2) design

**Status:** approved design, pre-plan.
**Date:** 2026-10-08.
**Parent:** [`2026-10-07-ssh-anywhere-design.md`](./2026-10-07-ssh-anywhere-design.md). This is Milestone 2 of that program. Cross-reference rule used throughout: **`§N` below means this document; `parent §N` means the parent.** This file elaborates where the parent summarizes, and it is decisive wherever it resolves a parent §16 open item.
**Base:** Milestone 1 (terminal + jump, PRs #334/#336/#337 on `feat/ssh-anywhere-1/2/3`) is unmerged and is the base; this work lands on the launcher seam M1 exposes, as its own spec and its own security review.

## 1. Goal and scope

Milestone 2 delivers relay mode: an interactive SSH pane that runs on a connecting machine **B** holding no signing key, authenticating to an arbitrary sshd-only destination **D** through the ssh-agent of a different machine **A** that does, over a shuttle the plane routes but cannot read. It ships the two things relay mode needs to be operable (the machine-identity roster and the key grants) and the act that turns a relay destination into a first-class node ("Set up Subshell here").

Done when the parent §17 M2 sentence holds: the same pane runs on a machine with no key at all, authenticating through a machine that does, with a CI test proving the plane sees only opaque envelopes and the key never leaves its home.

**In scope:** the per-machine signing identity and its enroll-time registration; the node-side machine pin store and its display/recovery; the sealed agent relay (proxy on B, responder on A, broker and blind router on the plane); the agent method allow-list and identity scoping; `ssh_key_grants` and the first-use approval that creates them; the M2 host-key pin path (`ssh_host_pins`); the destination upgrade; the matching UI, audits, and §13 tests.

**Out of scope (parent §2, parent §5.2 and parent §8 postures, stated together):** a general SSH-protocol proxy; X11 or agent forwarding toward D; port forwarding; any key custody or copying; multi-operator separation of duties; any change to the OS-user boundary. A `ProxyCommand` hop is refused at resolve exactly as in M1; relay is not a way to reintroduce it.

## 2. Terminology (adds to parent §3)

- **A / key home:** the machine whose ssh-agent signs. Needs `ssh_enabled` on (parent §4.3) and to be online for the handshake window.
- **B / connecting machine:** the machine that runs the pane and the `ssh D` process, holding no key. `ssh_enabled` on.
- **D / destination:** any sshd. Not gated; dialed to.
- **Signing identity:** the per-machine ES256 keypair introduced here, distinct from the ECDH-ES encryption pair already in `apps/node/agent/src/identity.ts` and from the plane-held ES256 command key in `control-keys.ts`.
- **Machine pin:** a byte-equality pin of a peer's public keys, signing and encryption halves alike (§4.4), held in a new node-side machine pin store (never the channels' `peers.json`).
- **Relay session:** a bounded plane-brokered pairing of (grant, A, B, pane/subshell id, opaque routing ref, lifetime).
- **TOFU:** trust-on-first-use; a key is pinned from the first copy received, and any later differing copy is refused.
- **Relay frame:** the new `/ws/node` link frame that carries one sealed envelope (§5.1).
- **Wire-frame census:** the repo convention (a `node-frames` test) that inventories every frame type; the relay frames join it.

## 3. The five open items, decided

These close the parent §16 list; each is elaborated in its section.

1. **Machine-identity bootstrap** (§4): the signing keypair is minted and its public half registered at **enroll**, and the node-side machine pin store is byte-strict. This removes a fresh first-use TOFU ceremony; it does not, on its own, move the parent §10 pre-first-pin window (§4.6 states that honestly), and the two machines' own loopback dashboards offer an optional out-of-band check.
2. **Destination upgrade** (§7): reuse ordinary enrollment over the machine's own connection. No #330 runtime-session re-port.
3. **Per-use approval on A** (§6): a first-use prompt creates a standing grant; later uses under it are silent. The approval is the creation act; there is no separate per-grant "ask each time" flag.
4. **A's identity source** (§5.4): agent-only. A's identity files are never read or served; a key becomes usable remotely only once loaded in A's agent.
5. **Relay-only destination auto-enroll** (§7): enrollment creates the node row; "Set up Subshell here" wires mint-key to run-enroll to the node appearing. No separate auto-enroll path.

## 4. Machine identity and pin store

### 4.1 A per-machine signing keypair

`identity.ts` generates and holds only the ECDH-ES encryption keypair; the ES256 key that signs node commands is plane-held (`control-keys.ts`), so no per-machine signing key exists. M2 adds one: the node generates an ES256 keypair at the same moment and posture as the encryption pair (0600 in the node data dir, private half never leaves the machine, replaced only by explicit re-enroll or key rotation). It signs the relay payloads of §5.6 and nothing else; it never authorizes a plane command on its own.

### 4.2 Register at enroll

The enroll route already writes the node's ECDH-ES public key into the identities store under the `node:<id>` principal. It now carries the signing public key in the same request, stored in the **same `node:` identities record** as a `signingPublicKey` field beside the existing `publicKey`. Because enroll is gated by a single-use, 24 h, operator-minted setup key, the signing key inherits that event's trust: it is bound to the deliberate act of attaching the machine, and node deletion cascades it exactly as the encryption key already does. Node key **rotation**, which today clears `encryptPublicKey` inside its transaction, clears `signingPublicKey` in the same transaction, so a rotated node's redial re-report fills an empty slot as a first registration rather than tripping §4.3's guard; peers that had pinned the old key recover through §4.5's re-pair.

### 4.3 Bootstrap for pre-M2 nodes

Nodes enrolled before M2 hold a signing keypair after the agent upgrades but have never reported its public key. A new signed command `ssh_register_identity` delivers the signing public key once over the already-authenticated, app-layer-encrypted node link, and the plane writes it into the `signingPublicKey` slot. This reuses the transport parent §5.3 requires (the peer key reaches the node "inside a signed command on the existing node link") for the node's own key at first contact. It is idempotent: a re-report of the same bytes is a no-op; a report of a **different** key than one already on file trips §4.3's own-registration guard rather than silently overwriting (a post-rotation re-report is exempt, because rotation emptied the slot first, §4.2); recovery is re-enroll plus per-peer re-pairs (§4.5).

### 4.4 The node-side machine pin store

Relay is always pin-strict. Each side keeps BOTH of the peer's public keys (the ES256 signing key of §4.1 and the ECDH-ES encryption key `seal`/`open` uses) in a **new** node-side store, a distinct file from the pane-side channels `peers.json`, read by its own path that never consults `SUBSHELL_CHANNEL_PIN`. When A first needs to verify or seal to B (or B to A), the plane brokers the pairing and delivers the peer's registered signing AND encryption public keys inside the relay-open command; the receiving machine writes both to the machine pin store and thereafter enforces byte equality on each, mirroring `pin-store.ts`'s comparison rule but never its escape hatch. Pinning the encryption key is what makes §5.5's blindness real: sealing uses the recipient's ECDH-ES key, so a plane that could hand B a plane-controlled encryption key for A would read every challenge, and this byte-equality block is what refuses it. A changed peer key (either half) is a hard block naming the peer and pointing at recovery (§4.5).

### 4.5 Pin display and recovery

The parent §5.3 gap "there is no operator-visible machine pin display or recovery flow" is closed by a **machine trust card** (§8): it shows this machine's own signing and encryption fingerprints and every pinned peer with both, each a short `SHA256:` base64 fingerprint over the key's public material, with a re-pair act. The preimage is pinned: agent keys (§5.4) hash their agent wire encoding, and the ES256/ECDH-ES machine keys hash their DER `SubjectPublicKeyInfo`, never a JSON-JWK serialization (which is not canonical), so the honest dashboard comparison of §4.6 is well-posed rather than serialization-dependent. The values are carried to the plane on the existing node **runtime report** (which `docs/security.md` §6 attaches only for an online agent node and only to owner or `edit` viewers, never `view` or `local`); an offline node shows the last-known card marked stale, which the plane can render because it mirrors the last reported fingerprint block durably onto the `nodes` row (§9) rather than reading only the live socket. The same own-and-pinned fingerprints are also rendered on the node's **own plane-independent loopback dashboard**, which is the plane-independent side of §4.6's check.

**Re-pair** replaces a stored peer pin after the plane re-delivers the peer's registered keys to A over the relay-open-style leg (§4.4), not the §4.3 self-report leg (which carries a machine's own key); it is owner-only and audited (`node.ssh_machine_pin.repair`, naming the peer id only). A machine whose OWN registration slot holds a wrong key recovers by re-enroll plus per-peer re-pairs. A genuinely rotated peer key is recovered this way; there is no "trust anyway" escape and no reuse of the channel escape.

### 4.6 What this defends, honestly

The parent §10 says the load-bearing word is "after": a plane compromised before A first pinned B can substitute its own key. Enroll-anchoring changes what is *stored*, not how A *learns* B's keys: A's first copy of B's signing and encryption keys still arrives inside the plane's relay-open command (§4.4), so the **residual window is exactly the parent §10's "a plane compromised before A's first pin of B,"** and it stays accepted under `docs/security.md` §0 like every other control-plane-compromise risk. Enroll-anchoring buys three real things: no fresh first-use TOFU ceremony (the key is already registered), byte-strict pins with explicit re-pair recovery, and a plane that cannot swap a key **after** A has pinned it without tripping the block. It does **not** close the pre-first-pin window.

The one control against it is a **post-hoc** out-of-band comparison in which neither side is plane-rendered. Because B's pin lands on A only at the first relay-open command (§4.4, §6.2), the very first handshake already runs on plane-delivered keys, so this is DETECTION after the fact, not prevention: a substituting plane that holds the substituted signing key keeps signing successfully, A's store is self-consistent under the substitution, and nothing trips mechanically. What the comparison gives is a way to notice. A's loopback dashboard shows the peer fingerprints it actually stored (from its node-local pin store, §4.5); B's dashboard shows B's own fingerprints computed locally from its private keys; a mismatch means the plane substituted, and the remedy is manual: revoke the grant, re-enroll, and re-pair (§4.5), not an automatic stop. Reading the plane's approval screen is worthless here, since that screen is plane-rendered; only the two dashboards count. Preventing the first substituted handshake would need pins delivered out of band before any relay, which this milestone deliberately does not build: the mandatory-fingerprint variant was considered and rejected as per-pair ceremony the single-operator posture does not demand. Skipping the comparison altogether leaves the parent §10 window open, accepted under `docs/security.md` §0.

## 5. Relay runtime

The parent §8 protocol governs, with two declared deviations: §5.4 supersedes its snapshot-files identity-filter clause (B-resolved paths are not portable to A's agent), and here the relay is route-only, so parent §8's "the plane stores envelopes" phrasing describes the channels precedent, not this posture (it stores none durably). This section pins the pieces and the transport decision.

### 5.1 Transport: node-link relay frames

The sealed envelopes ride the `/ws/node` link, not the browser-facing `/api/channels` path. The reason is fixed in parent §5.3: the node daemon holds **no REST credential**, so it cannot post to a channel; the node link is its only authenticated, encrypted, low-latency, bidirectional transport, already app-layer encrypted since protocol 14 and authenticated by the node key. It also fits the traffic: the agent exchange is bidirectional (B to A requests, A to B responses) and bursty over seconds, which the one-shot plane-to-node command/reply model serves poorly and a channel log serves only by persisting traffic it should not keep.

Concretely: the plane sends A and B each one signed **open** command carrying the full pairing: the relay-session id, the opaque routing ref, both node ids with their roles (naming each machine as A or B), the peer's registered signing AND encryption public keys to pin, the grant id and its selected key-fingerprint set (§6.1, the set delivered so A's responder can enforce it without a REST call it cannot make), and the lifetime. After that a new lightweight frame type on the open link carries sealed blobs both ways keyed by the routing ref, with **no per-message command signing**: the link already authenticates the machine and origin comes from the inner ES256 signature (§5.6), so signing each frame is redundant on a stream. The plane matches the two links by routing ref and forwards the opaque blob unopened. **Open, route, close** are the plane's only roles in a payload's life. A relay frame is capped by a new `SSH_RELAY_FRAME_MAX_BYTES` (bounded to the channel envelope scale); an over-cap frame is refused and the session closed with a named reason, matching the repo's posture that wire caps are law.

This adds a link frame type, so **M2 carries its own `NODE_PROTOCOL_VERSION` bump, 17 to 18**: the ssh_enabled bump the parent §4.3 required and M1's own ssh-launch bump were already consumed at tiers 16 and 17, so an agent shipping with M1 speaks tier 17 and would otherwise pass the exact-match gate while understanding no relay frame. The 17 to 18 bump is what makes §11's pre-bump refusal and §13's bump gate true.

### 5.2 B: the agent proxy socket

The launcher exports a scoped `SSH_AUTH_SOCK` (parent §5.4, into the `ssh` invocation only) pointing at a Unix socket B's node creates in the pane's per-session ssh directory (`<dataDir>/ssh/<pane-id>/`, the M1 dir), mode 0600, beside the rendered config. The socket speaks the ssh-agent wire locally: each request is framed, sealed to A, and handed to the plane as a relay frame; each reply is opened and written back. It exists only for the handshake window (§5.6 lifetime), then is torn down; the established pane needs no agent afterward (parent §8: rekeying re-verifies the host key, not the client agent).

### 5.3 Plane: the broker

The plane brokers a pairing only when a live grant is used (§6). In memory it holds the relay session (grant id, A, B, pane/subshell id, routing ref, expiry) plus a per-node concurrent-relay-session cap `SSH_RELAY_MAX_PER_NODE`, whose exceedance is a loud refusal; durable it writes only audit rows (§9). It never holds the agent payload; that lives solely inside sealed envelopes it shuttles. Teardown fires on the signals in §5.6 (handshake established, lifetime expiry, A dropping, grant revoke).

### 5.4 A: the responder

A's responder accepts an **agent-protocol** request only when the plane brokered it for a live grant on a session naming this A. (The roster command below is the one non-agent exception: it is a node-link signed command like `detect`, answered with no grant outstanding.) Two rules:

**Method allow-list, default-deny.** Forward exactly the two request types SSH publickey auth uses, `SSH2_AGENTC_REQUEST_IDENTITIES` and `SSH2_AGENTC_SIGN_REQUEST` (by symbolic type, matched on the wire); **refuse every other type**: all identity mutations (`ADD_IDENTITY`, `ADD_ID_CONSTRAINED`, smartcard add/remove, `REMOVE_IDENTITY`, `REMOVE_ALL_IDENTITIES`), `LOCK`/`UNLOCK`, `EXTENSION`/`EXTENSION_RESPONSE`, every SSH1-era code, and any unknown type. A granted window therefore cannot mutate or lock A's agent against its other panes, by default-deny rather than a name list that could miss a code.

**Identity scoping, cross-machine.** A's `REQUEST_IDENTITIES` answer is served **filtered to the key fingerprints the grant names**, not A's whole roster and never by matching the snapshot's identity *paths* (those are resolved on B and are not portable to A's agent, which carries blobs plus comments). At the first-use approval (§6.2) the operator selects which of A's public agent identities may serve the grant; their fingerprints are stored on the grant (public data, no secret), capped by a new `SSH_MAX_GRANT_FINGERPRINTS` (kept distinct from `SSH_MAX_IDENTITY_REFS`, which bounds snapshot paths, not grant selections). A grant naming no fingerprint serves nothing (which reads as "no matching key in A's agent," parent §12). The same set gates signing: a `SIGN_REQUEST` arrives with a key blob, and the responder refuses a `SIGN_REQUEST` whose key blob hashes (SHA-256 over the agent wire encoding, `SHA256:` base64) outside the grant's selected fingerprint set, checked at the responder and never forwarded to A's agent, so a granted window signs only the keys the operator picked regardless of which blob B supplies.

**Roster enumeration for approval.** So the operator has something to choose, the plane sends A a signed `ssh_agent_identities` node-link command (like `detect`, answered with no grant outstanding and no relay session) that asks A's agent for its public identities as `SHA256:` fingerprints plus comments, blobs withheld. It answers only what is asked and writes no audit row; it fails closed if A is offline (§11). Each fetch hands the plane A's whole public roster and labels, new plane-side metadata (§10).

**Agent-only (§3 item 4).** The responder talks to A's running agent socket and nothing else. A private key that exists as a file but is not loaded in the agent is absent from the roster; Subshell never opens a private key file to compute a match, so key bytes never move and no passphrase path exists on A.

### 5.5 Plane blindness, for the record

The envelope format is `packages/mcp-core/src/crypto.ts` `seal`/`open` (ephemeral-static ECDH-ES+A256KW, A256GCM, plaintext recipient-id header for blind routing). Each side seals to the peer's **pinned** encryption key (§4.4), so plane blindness rests on the byte-equality pin, not on the plane's honesty. The plane reads the routing ref to pair and nothing else. A wire capture at the plane during the §13 crown-jewel test (parent §14) shows opaque envelopes and plaintext routing ids only.

### 5.6 Origin, replay, and lifetime

Confidentiality is not authenticity: anyone holding A's public key, the plane included, can craft a seal A opens (`crypto.ts` `seal` is ephemeral-static with only a plaintext recipient header). Origin rides a signature, not the seal: the sender signs the inner payload with its machine signing key and the receiver verifies against its **machine pin** of the sender (§4.4), reusing the ES256 JWS precedent from node command signing, the signature living inside the sealed envelope so the plane never sees it.

**Replay.** Two session nonces bind the pair and are contributed by the endpoints, not the plane: B's first sealed request carries a fresh 128-bit `nB` and A's first sealed response a fresh `nA`, and each side records the peer's value and signs it into every later message. Anti-replay is per direction by a **monotonic sequence number** inside the signed envelope: the receiver keeps the highest `seq` seen for each direction and rejects any message whose `seq` is not strictly greater, so a multi-key handshake (several `SIGN_REQUEST`s in one session) completes while a byte-identical resend is refused. The ES256 signature covers a canonicalized inner message of the relay-session id, the routing ref, a direction tag, the `seq`, the agent bytes, and whichever session nonces the sender knows at send time (`nB` alone in B's first message; both once each side has seen the peer's), and the receiver verifies against what it holds. A resent or non-increasing-`seq` envelope is refused even though the plane **routes every envelope and can resend any of them** (it stores none durably). Cross-session replay is closed by the signature covering the relay-session id: an old envelope cannot ride a later session unless the plane mints a colliding id, and if it did the survivor is a stale-challenge signature inert outside the already-closed D connection, self-DoS the plane already holds rather than a forgery.

**Lifetime.** The parent §8 method allow-list, no-forwarding-toward-D, and handshake-window lifetime bullets are adopted; within the allow-list bullet the clause filtering identities to the snapshot's named identity *files* is superseded by §5.4's fingerprint set (B-resolved paths are not portable to A's agent), which is the deviation §5 declares. The relay lifetime is a new named constant in `ssh-limits.ts` (the existing `SSH_SESSION_OPEN_DEADLINE_MS` of 30 s is its model), and the handshake-completion signal is defined because B's proxy cannot see ssh's handshake to D: B tears the proxy down when the `ssh` child has been alive a grace period with no agent error (and immediately on child exit), with the hard lifetime cap as the ceiling and A-drop and grant revoke as earlier cuts.

## 6. Grants and the first-use approval

### 6.1 The grant record

`ssh_key_grants` (parent §7): id, owner, name, key-home node id (A), **resolved** destination selector, and the selected key-fingerprint set (OpenSSH `SHA256:` base64 over the key's public material, the same canonical form the trust card shows). No secret, no key bytes. The selector is matched against the resolved destination hostname (parent §7); an alias typed at approval is **resolved to the concrete `host` at grant creation and stored resolved, the alias kept only as display metadata**, so a later `~/.ssh/config` edit cannot silently re-point the grant, honoring the same canonical-destination rule parent §11 applies to saved hosts and pins. Host-key pins are **not** part of a grant; they are per resolved `user@host:port` (§9, `ssh_host_pins`), so one selector over many hosts yields many pins.

### 6.2 First use creates the grant

The first time a launch would route through an `(A, destination)` combination with no standing grant, the plane records a durable pending grant-approval row (§9) and notifies A's owner via a new owner-addressed kind in `notify.service.ts` (whose existing surface is subshell-shaped and needs one added kind), then **B's launch fails fast** with a loud, named refusal ("asked <A> to approve, connect again once approved"), never hanging a pane on a human. A's operator answers on the grants screen (a new approve/deny affordance, modeled on the signup `pending-approvals.ts` queue), which shows the requester, the destination, and A's own public agent identities to choose from (enumerated by the §5.4 `ssh_agent_identities` command; with A offline the screen cannot offer a selection and the request stays pending until A is reachable). It may display B's registered fingerprint, but that value is plane-rendered and for display only, never the §4.6 check (which reads off the two dashboards). **Approving** selects the key fingerprints and writes the grant plus A's selection; B's pin lands on A at the retried launch's relay-open command (§4.4), not at approval. **Denying** writes the `node.ssh_grant.deny` audit row but no grant and no pin; **expiry** (bounded, at setup-key scale) writes nothing at all. Later uses under a matching grant are silent. There is no separate per-grant "ask each time" flag: the first-use prompt already carries that role, and the residual scope risk is bounded exactly as parent §8 bounds it (an agent sign request carries no destination, so a grant cannot bind the agent to a host at the protocol layer; that residual is accepted under the single-operator posture and bounded by the fingerprint set plus instant revoke).

### 6.3 Matching, management, and revoke

The match predicate is (owner + the A chosen in the launch + the grant's resolved selector matched against the resolved destination). **B is not part of the grant's scope:** a grant authorizes reaching the destination with A's selected keys from any of the owner's connecting machines, and the approval copy says so plainly (under the single-operator posture this is a disclosure note, not a privilege widening). When multiple grants match one launch, the most specific selector wins, ties break to the oldest grant, and a distinct key home is disambiguated by the A the operator picked at launch. Revocation is instant and cuts both ways: the plane row goes and any live relay session using it is torn down so signing stops mid-session. Creation via the screen and via first use write the same row and the same audit event.

## 7. Destination upgrade: "Set up Subshell here"

A secondary act inside an open SSH-terminal pane on D. It does not re-port #330's brokered runtime session. It reuses ordinary enrollment: the plane mints a setup key (existing route) and the act drives the standard `install.sh` enrollment on D, so D dials the plane and becomes an ordinary enrolled node, exactly as if the operator ran the one-liner by hand.

**Transport, stated so the key stays off shared surfaces.** The command runs on D as a **non-interactive `ssh D '<install command>'` exec on its own short-lived connection**, separate from the interactive pane; the minted setup key is therefore never typed into the pane (so it reaches neither the pane screen, which streams to view-grantees, nor B's pane log). The act never echoes raw installer output: the current `install.sh` prints the *unspent* key on its 404 advice branch, so the act runs a small parser that emits only a controlled status verb (success, or the named egress/other failure) and redacts any line matching the setup-key shape; the installer's 404 line is itself fixed to print `--key <setup key>` rather than the value. The setup key therefore surfaces only where the accepted postures already allow a non-secret credential: briefly in **B's and D's process tables** while the exec and install child run (the `ps`-visible-argv posture), and in the plane's request/access log only if it rides an install URL (the enrollment-link posture); a non-interactive `sh -c` exec does not append to shell history, so D's history is generally not a sink. Its life is single-use and at most 24 h; it is an enrollment credential, not SSH key material, and `node.ssh_upgrade.run` (§9) never names it, matching the `setup_key.create` no-metadata precedent.

**Completion and failure.** Success is the new node's `ready`/enroll event, awaited with a bounded wait; a midway failure names the stage. If D cannot reach the plane (no egress back to the plane URL), the act refuses cleanly with that named cause, distinct from any key error, and the working pane is unaffected. A relay-only destination becomes a first-class node **by enrolling**, because enrollment is the only way a node row is ever created, so the parent §16 "auto-enroll after set up here" collapses into this act.

## 8. UI (adds to parent §11)

- The destination-first flow is unchanged; its step-2 follow-up "sign with [machine]'s keys" now resolves to a relay and the grant/approval path (§6).
- **Grants screen:** list, create, edit the selector/name, revoke, and answer pending grant-approvals (§6.2); owner-scoped, under SSH settings.
- **Machine trust card** (the card §4.5 defines): this machine's own signing and encryption fingerprints, every pinned peer with both, and a re-pair act each; fed by the runtime report, so it renders for owner or `edit` viewers only (never `view` or `local`) and is stale-marked offline. Surfaced on the node detail.
- **Host-key display:** destination pins visible; the changed-key refusal is surfaced on the failed connect.
- **"Set up Subshell here":** an act in the SSH-terminal pane, not a landing-screen mode (parent §11's destination-first landing stays intact).

Copy follows the design system: role tokens only, at most two sentences per explanation, no em dashes.

## 9. Data model and audits (adds to parent §7; audit names to `docs/security.md` §10)

**Schema.** A signing public key per node, in the identities-store `node:` record's `signingPublicKey` slot (§4.2). Tables `ssh_key_grants` and `ssh_host_pins` (parent §7 M2 rows; both ship now). Relay session state is in-memory on the plane with a durable audit row, no table. The last runtime-report ssh-fingerprint block is mirrored onto the `nodes` row so the trust card survives an offline node or a plane restart (§4.5). The §6.2 pending grant-approval is a **durable** `ssh_grant_requests` row (borrowing the `pending-approvals.ts` signup-queue shape: owner, request, and an expiry sweep), so a plane restart does not forget outstanding approvals; because B already failed fast, a re-launch simply finds the pending row. Node-side: the machine pin store file (§4.4), separate from `peers.json`. The `ssh_enabled` column and mirror ship in M1. New constants in `ssh-limits.ts`: `SSH_RELAY_FRAME_MAX_BYTES`, a relay-lifetime constant modeled on `SSH_SESSION_OPEN_DEADLINE_MS`, and `SSH_RELAY_MAX_PER_NODE` (the §5.3 concurrent-relay-session cap), a handshake-teardown grace constant for §5.6, and `SSH_MAX_GRANT_FINGERPRINTS` (§5.4).

**New audit events** (ids/hosts/field-names only; never payload, challenge, or signature):

- `node.ssh_identity.register` (enroll-time registration, and the pre-M2 link delivery, distinguished by a `via` field).
- `node.ssh_grant.request|create|update|delete` and `node.ssh_grant.approve|deny` (request names the launch that asked, A, B, and destination; approve names the chosen key fingerprints and destination; never any key material).
- `node.ssh_machine_pin.repair` (the §4.5 re-pair, naming the peer id only).
- `node.ssh_relay.open|close` (open names grant/A/B/pane and routing ref; close names the reason).
- `node.ssh_host_pin.create|delete` (a changed D host key is the parent §9 hard block; recovery is delete plus a fresh grant-creation TOFU, no separate rotate act).
- `node.ssh_upgrade.run` (the §7 destination upgrade, naming D, the grant, and the outcome; never the setup key).

The relay metadata the plane always held (which machines talk, timing, sizes, routing ids) is disclosed by parent §10 as retained, not new.

## 10. Trust model delta (refines parent §10)

Gained, beyond what parent §10 lists: the plane never reads an agent payload, which now rests on the recipient's **encryption** key being pinned (§4.4, §5.5) rather than on the plane's honesty; after A has pinned both of B's keys a plane cannot swap either without tripping the byte-equality block. A's responder enforces a fingerprint set the plane delivers (A has no REST path to fetch it), so a plane could widen the set it hands A; that widening sits inside `docs/security.md` §0's control-plane acceptance; no plane-independent surface shows which set A's responder enforced (the §4.5 dashboard carries machine pins, not the grant's agent-key set), so the durable record of the operator's selection is the `node.ssh_grant.approve` audit row naming the chosen fingerprints (§9). Agent-only (§5.4) removes a class of exposure: no identity file is read, no passphrase prompt lives on A, no key file transits. A grant revoke cuts a live session. The residual is precisely parent §10's "a plane compromised before A's first pin of B," accepted under `docs/security.md` §0 and detectable after the fact by the optional §4.6 dashboard comparison (which prevents nothing before first use); it is **not** narrowed by enroll-anchoring, and this spec does not claim it is. A compromised B inside its own granted window is still bounded by the default-deny allow-list and the fingerprint set (parent §10), unchanged. The `ssh_agent_identities` fetch (§5.4) discloses A's whole public roster and labels to the plane on every call, fingerprints and comments only and no blobs, accepted under `docs/security.md` §0 like the rest of the retained metadata.

## 11. Failure modes (parent §12, plus M2)

Parent §12 stands in full (A offline before handshake, no matching key, changed host key, no-reach vs no-key, relay expiry mid-handshake, loud quota/policy refusal). Add:

- **Approval requested, unanswered:** B's launch failed fast with the named refusal; the pending approval expires at its bound writing nothing (§6.2).
- **Roster fetch with A offline:** the approval screen cannot enumerate A's agent identities, so a first-use request stays pending until A is reachable (§5.4, §6.2).
- **No signing key on a node** (a pre-M2 node not yet delivered, or a corrupt store): name the machine and offer the identity register act (§4.3); never proceed unsigned.
- **Peer key changed** (either the signing or encryption half) since pinning: hard block naming the peer, pointing at re-pair (§4.5).
- **Node key rotation:** clears both registration slots (§4.2), the node re-reports on redial, and every peer must re-pair it (§4.5); a stale peer pin blocks until re-paired.
- **D cannot reach the plane during "Set up Subshell here":** a clean egress refusal, the working pane untouched (§7).
- **Reverse verification fails:** B rejects a response whose A signature does not match its pin of A; the handshake fails cleanly rather than hanging.
- **Relay attempted through `local`:** not offered; both relay roles require the node-agent surfaces (§15), so the server's own `local` node does not serve as A or B.
- **Over-cap relay frame:** refused, session closed with a named reason (§5.1).
- **Relay frame on a pre-bump agent:** the 17→18 `NODE_PROTOCOL_VERSION` exact-match gate refuses pairing before any relay command, naming the agent-upgrade remedy, never half-relaying.

## 12. Security rules honored (parent §13)

Parent §13 stands; these are where M2 leans on it. No SSH key, challenge, or signature in any log, argv, audit row, or notification. `SSH_AUTH_SOCK` scoped to the ssh invocation only; the agent proxy socket and rendered config 0600 in the per-session dir, removed with the pane. `shellQuote` on every built-command token. The relay open/close are signed commands and relay frames ride the authenticated, encrypted link, with origin the inner ES256 signature. Machine-to-machine payloads reuse `mcp-core` seal/open and the TOFU byte-equality rule in the separate always-strict machine store, never a bespoke cipher and never honoring `SUBSHELL_CHANNEL_PIN`. The destination-upgrade act runs non-interactively so the enrollment setup key stays off the pane and B's log, surfacing only in the accepted process-table and install-URL postures (§7); it is an enrollment credential, not the SSH key material this section never logs. Static imports only. An agent-capable SSH pane stays view-only to sharees (parent §5.4). Outbound SSH stays gated per node, default-off, fail-closed.

## 13. Testing

The parent §14 M2 list is required. Add coverage for these decisions:

- **Units.** Enroll registers `signingPublicKey` beside `publicKey`; `ssh_register_identity` pre-M2 delivery is idempotent and a changed key trips the block; node key rotation clears `signingPublicKey` so the redial re-report is a first fill, not a block. The machine pin store is byte-equality strict on BOTH the peer signing and encryption keys, is a separate file from `peers.json`, ignores `SUBSHELL_CHANNEL_PIN`; substituting either half after pinning blocks naming the peer; re-pair replaces the pin and unblocks, and without it the block persists. The runtime report carries own and pinned-peer fingerprints; the loopback dashboard renders them from the node's local store while the trust card renders from the report's carriage; an offline node stale-marks; a fingerprint is canonical `SHA256:` base64 so the honest compare is well-posed. The `ssh_agent_identities` command returns A's agent identities as fingerprints plus comments with blobs withheld, is refused unsigned or by a wrong origin, and writes no audit row. Grant CRUD and the match predicate (resolved selector, most-specific-wins, oldest-tie); an alias typed at approval is stored resolved so a config edit does not re-point it; the first-use approve path creates the grant (B's pin lands on A at the retried relay-open), deny writes only the `node.ssh_grant.deny` row while expiry writes nothing, and a matching grant serves silently on second use; a durable `ssh_grant_requests` row survives a plane restart and is swept at expiry. Identity scoping: only the grant's selected fingerprints are served, the responder never opens a private key file, and a `SIGN_REQUEST` whose blob hash falls outside the set is refused. Method allow-list: every request type in OpenSSH's `agent-proto.h` is enumerated and only `REQUEST_IDENTITIES` and `SIGN_REQUEST` forward. Replay: a multi-key session (several `SIGN_REQUEST`s at increasing `seq`) completes, while a resent or non-increasing-`seq` envelope is refused. `NODE_PROTOCOL_VERSION` 17 to 18 gates a pre-bump agent; an over-cap relay frame is refused and the session closed; exceeding `SSH_RELAY_MAX_PER_NODE` is a loud refusal. Host-pin render into `UserKnownHostsFile` with `StrictHostKeyChecking=yes`; a mismatched pin blocks naming D, and delete-plus-fresh-grant TOFU recovers after a changed D key.
- **Integration.** Two in-process machine identities A and B over a fake plane broker: a sign request reaches A's stub agent and returns sealed; a non-allow-listed agent method (e.g. `ADD_IDENTITY` or `REMOVE_ALL_IDENTITIES`) is refused at the responder; an ungranted or wrong-origin **agent** request is refused while `ssh_agent_identities` is accepted with no grant outstanding; a relayed blob is byte-opaque at the fake plane; a captured envelope replayed inside the window **and** replayed into a later session with a reused routing ref is inert; a `SIGN_REQUEST` naming an ungranted blob is refused even after a correctly filtered identities answer; and **B rejects a bad A response signature** (reverse direction).
- **End to end (the crown jewel).** Per parent §14: A holds the key in its agent, B holds none, B authenticates to D through the plane relay; the plane-side wire capture shows only opaque envelopes plus plaintext routing ids; the key never appears on B or the plane. Extend it: a grant revoke between handshake and D is refused; and "Set up Subshell here" turns an egressing D into an enrolled node without the setup key appearing in B's pane log.
- **CI regime** per `verification.md`: focused files while iterating, full trio plus `lint:prose` at the boundary, e2e under the serial container, `env -u SHELLOPTS -u BASHOPTS` for shell-spawning suites, never the live `:3080`, never run the M2 migration against a live DB.

## 15. Non-goals and accepted risks (carry-forward, do not "fix")

The single-operator posture is unchanged. The plane retains denial-of-service and metadata (parent §10). The parent §10 pre-first-pin window is accepted under `docs/security.md` §0; the §4.6 comparison (both values off the two machines' own dashboards) can DETECT a pre-first-pin substitution after the fact on the operator's initiative, but neither prevents it before first use nor is mandatory. A grant cannot bind the agent to a host at the protocol layer, so exposure is bounded by the fingerprint set and instant revoke rather than host binding. The agent proxy is transient and never forwarded toward D. There is no key custody, no identity-file read, and no passphrase handling. Relay needs A online for the handshake; an offline A is a clear error, never a copy-the-key fallback. Both roles also depend on the node-agent pin store, runtime-report carriage, and loopback dashboard, so the `local` server node (no agent link or dashboard) does not serve as A or B in relay mode; `local` keeps M1's direct and jump paths, and `local` relay is deferred rather than half-built here.
